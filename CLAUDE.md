# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal projects repository — primarily background automation apps, with occasional MAUI mobile apps and Angular frontends. Projects are added incremenledger; update this file with project-specific build/test commands when a new one lands.

## Design

**`DESIGN.md` at the repo root is the Paper & Ink design bible** — the single source of truth for palette, typography, motion, materiality, spacing, components, PDF page specs, icon specs, voice, and accessibility across every project. Rules that matter when writing code:

- **No color hex or type-size literals outside the registered token files** (DESIGN.md §16). Leak-guard unit tests in every project enforce this; consume tokens instead (`Codex.Domain.Design.DesignTokens` + `Codex.Ui.Android` `PaperUi`/`PaperTheme` for FocusPhone, `Storyboarder.Domain.Design.DesignTokens` + `Resources/Styles/DesignTokens.xaml` styles for the MAUI apps).
- The six shared fonts live in `/Fonts` (Source Serif 4, Source Sans 3, Cascadia Code — static TTFs, OFL). Native heads package them as assets via `Codex.Ui.Android`; MAUI heads via `<MauiFont>`; the Skia renderers via embedded resources (`EmbeddedTypefaces`).
- **Interaction rules are load-bearing** (DESIGN.md §5–§11): success is an inline state change (no success toasts/alerts), destructive acts are undo-first (an `UndoBar` window, not a confirm dialog), loading is a status sentence not a spinner, primary actions live in a pinned bottom bar, screens open with a Serif in-page header, time is 12-hour and list timestamps are relative (`RelativeTime`/`TimeFormats`, duplicated per Domain and kept identical by a parity test).
- **Generated artifacts** (icons, the paper-grain tile, the owner branding medallion) are all produced by the committed **`Tools/IconStudio`** console: `dotnet run --project Tools/IconStudio -- --repo-root .` (tests: `dotnet test Tools/IconStudio.sln`). Never hand-edit generated resources. **Owner photo swap:** drop a square image at `/Branding/owner.png` and rerun IconStudio — it circle-masks the photo into the medallion for every consumer (PDF covers + settings screens) and never clobbers an existing `owner.png`.
- **Owner's voice is pending** (DESIGN.md §11): the intent is to learn the owner's wit from their self-authored Google Drive docs, which needs the Google Drive connector authorized in claude.ai. Until then copy stays quiet-neutral.
- New projects start on-system: see DESIGN.md §15 for the MAUI/Angular defaults.

- **Podcast fetch speed (cold-start cache + parallel refresh):** episodes were never persisted — every launch rebuilt them in-memory and opened on a blank "Fetching episodes…" while feeds fetched **sequentially** (N shows = N serial round-trips). The refresh is **cache-preserving**: it starts from the cached episodes pruned to still-subscribed feeds and only replaces feeds that fetched successfully, so a flaky network keeps a show's last-known episodes instead of dropping it; per-feed failures are summarized in one toast rather than a wall of them. Now `MusicScanner` is **incremental**: it diffs the Drive listing against the cache's stored per-file change signature (modified-time + size — new `modifiedTimeTicks`/`sizeBytes` columns, added to old caches by an in-place `ALTER TABLE` migration) via the pure, unit-tested `MusicScanPlan.Compute`, then only re-reads new/changed files and deletes tracks whose file is gone (no more clear-and-rebuild). The tag reads run in **bounded-parallel batches** (`MaxConcurrentReads = 8`, `Task.Run` + `Task.WhenAll`) — bounded to respect the Drive quota/mobile radio and because `MusicCatalogCache` is a single `SqliteConnection` (not safe for concurrent writes), so each batch of parallel reads lands in **one serialized transaction** (the versioned `Upsert` overload). Progress is reported over the files actually being read, so a rescan that changed little finishes fast. `MusicScanPlan` + the cache versioning are unit-tested; the scanner's Android wiring is compile-checked in CI.

### Canonizer (project folder `Storyboarder/`, namespaces `Storyboarder.*`)

An **Android (MAUI) app** — user-facing name **Canonizer** — that reads a novel manuscript and produces a **revision report** as its star product, with **one wordless image per scene as supporting evidence** (a fidelity check: does the beat land visually as written?). It pivoted from a graphic-novel factory ("Storyboarder"); the **internal identity is deliberately unchanged** (namespaces `Storyboarder.*`, solution, `StoryboarderDbContext`, `storyboarder.db`, app id `com.storyworthtelling.storyboarder`) so an installed build upgrades in place — only the user-facing name, the icon (a **red pen nib**), and some domain concepts changed. Four **load-bearing principles**: **nudge never write** (diagnose & point, never ghost-write prose/lines) · **both ends of the pendulum** (flag under- *and* over-writing) · **the report is the star** (the image is evidence) · **quiet by default** (silent Drive delivery, one in-app note, no push/toast). Pipeline (all state in the DB, one unit of work per worker cycle, resumable): `Ingesting` → `BuildingDesignBible` (per-chunk analysis + reference sheets on the **strong** Claude model) → `RenderingSceneImages` (one wordless portrait per scene) → `ComposingAnalysis` (map-reduce the manuscript into the report — a **story half** and a **craft half**, two Claude calls persisted separately because one reply can't carry both, plus a separate resumable **voice-consistency** call `AssessVoiceConsistency`; rendered to raster pages via SkiaSharp and wrapped by the image-based PDF composer) → `Archiving` (deliver to Drive) → `Completed`. Modeled on DailyLoader: an AndroidX **WorkManager** periodic worker drains the pipeline on-device (no web host, no SignalR). See `Storyboarder/`.

- Tests: `dotnet test Storyboarder/Storyboarder.sln -p:StoryboarderTfms=net10.0` (Domain + Infrastructure + Tests; no device, no API keys — external services are faked). The `-p:StoryboarderTfms=net10.0` switch builds Infrastructure for the desktop TFM only so the suite runs without the MAUI/Android workload.
- Android head (`Storyboarder.Android`, `net10.0-android`, app id `com.storyworthtelling.storyboarder`): build with the MAUI/Android workload + Android SDK (same minimal-SDK note as FocusPhone — `platforms/android-34/`, `-p:AndroidSdkDirectory=<sdk> -p:AndroidUseApkSigner=false`); signs with the default debug keystore. Background work uses `Xamarin.AndroidX.Work.Runtime`.

- **Cross-draft history (Phase 2, the revision loop):** findings are first-class **`Finding` rows** (`Domain/Model/Entities.cs`, enums `FindingCategory`/`FindingStatus`) keyed by a stable **`ThreadId`** — the same issue across every draft of a project — with a first-class `Category` and a per-occurrence `Status` (`New`/`Carried`/`Regressed`; **Fixed is derived** from a thread's absence in a draft). A resumable `ComposeAnalysis` sub-step (gated by `BookAnalysis.FindingsReconciled`) gives each draft's findings their identity: a new **`IClaudeAnalysisClient.ReconcileFindings`** call matches this draft's freshly-consolidated findings against the prior draft's threads even after the wording moves, and the pure, unit-tested **`FindingReconciler`** (`Domain/Analysis`) applies those decisions (match-to-open→Carried, match-to-fixed→Regressed, unmatched→New; a prior open thread nobody claims→Resolved). **Scenes gain cross-draft identity** too (`Scene.PreviousSceneId`/`Changed`): the pure **`SceneMatcher`** (`Domain/Text`, normalized-text + token-set Jaccard) pairs a new draft's scenes to the prior draft's, so `RenderSceneImages` **reuses an unchanged scene's rendered image** (copied forward, render skipped) and only **changed/new scenes re-render** — a changed scene keeps its predecessor for a **before/after image pair**. A **running story-state** threads chapter-to-chapter through the map call (`AnalyzeChapter`'s `priorRunningState` + `ChapterNotes.RunningState` → `Novel.ContinuitySummary`) for long-range continuity and regression detection. `GetDraftDiffAsync` reports resolved/new/regressed by `ThreadId` plus the before/after scene pairs; the report PDF adds a "Since draft N−1" summary and inline `[new]`/`[regressed]` tags (a `DraftReview` the composer takes), and `DraftDiffPage` renders the before/after scene pairs. First-class `Finding` history + regression + before/after pairs is the Phase-2 delivery.
- **Expansion engine (Phase 3, additive feedback):** because the owner's early drafts run *short*, the report is **additive** — it surfaces scenes/beats to **add**, never drafted prose (nudge-never-write). A resumable `ComposeAnalysis` sub-step (gated by `BookAnalysis.ExpansionJson`) runs a new **`IClaudeAnalysisClient.ProposeExpansion`** call from the per-chunk notes (which now also gather `SummarizedMoments`/`ThinSpots`/`OffPageEvents`) + running story-state + measured word count + genre, returning an **`ExpansionReport`** (`Domain/Analysis`): ranked **`SceneAddition`s** (`AdditionKind` MissingBeat/CharacterDeepening/TensionStakes/ThemeDeepening, Must/Should/Consider), two-sided **`ShowTellNote`s** (`ShowTellDirection` Dramatize the summarized / Tighten the over-shown — the main lever for adding words), and a **`LengthAssessment`** framed by the pure, unit-tested **`LengthGap.Describe`** (how far short of the genre norm). Folded into the report via `WithExpansion`; the renderer opens with the length line and adds a **"Show vs tell"** section + a **"Scenes to add"** section (grouped by tier, ahead of the revision plan), mirrored in `ReportPage`. The additive read is per-draft (regenerated each draft, like the report body).
- **Series awareness (Phase 5, cross-book continuity):** links related **books** so a sequel reuses the prior book's canon. A "project" (a `ProjectId` group of drafts) is one book; a **series** groups books via three denormalized `Novel` columns mirroring the draft pattern — **`SeriesId`** (the series key, null = standalone), **`PreviousBookId`** (the prior book's canon-source draft, the book-level analogue of `PreviousDraftId`), and **`SeriesSequence`** (book number, the "Book N" badge) — carried onto every draft of a linked book (`Phase5SeriesAwareness` migration). **`ProjectService.CreateNextBookAsync`** starts a sequel as a **new project** (its own draft chain) linked to the prior book: it establishes the series (backfilling `SeriesId`/sequence 1 onto book 1's drafts), resolves `PreviousBookId` to the prior book's **latest-completed** draft, and sets the next sequence; `CreateNextDraftAsync` carries the three series fields forward. Three reuse mechanisms: (1) **returning-entity image reuse** — `ReviewProcessor.CarryForwardSeriesEntities` (folded into `ConsolidateBible`, the book-level mirror of `CarryForwardScenes`) copies a returning character/place's rendered reference image from the prior book (matched by name/alias, kind-scoped) so it stays visually on-model, keeping this book's own description; (2) the **Series continuity read** — a resumable `ComposeAnalysis` sub-step **2f** (gated by `BookAnalysis.SeriesContinuityJson` + `PreviousBookId`, billed once like the other reduce halves) runs a new **`IClaudeAnalysisClient.AssessSeriesContinuity`** call over a **`SeriesCanon`** (`Domain/Analysis/SeriesModels.cs` — the prior book's cast/settings, final `ContinuitySummary`, and open finding threads) built by `LoadSeriesCanon`/`LoadOpenThreads`, returning a **`SeriesContinuity`** (`SeriesBreak`s = contradictions of prior canon; `CarriedThread`s = prior open threads tagged Addressed/Ignored/Contradicted), graceful-empty like `ProposeExpansion`; (3) **carried findings** — the prior book's open threads are surfaced through that read (a problem spanning books, tracked), leaving the per-draft finding reconciliation untouched. Folded into the report via `WithSeriesContinuity`; `AnalysisDocumentRenderer.RenderSeriesContinuity` adds a **"Series continuity"** section (after voice consistency) that stays **silent** for a standalone book or a clean sequel (quiet by default), mirrored through `GetReportAsync`. The Android head adds a **"Start next book (new manuscript)"** card action (`NewProjectPage.PreviousBookId` mode → `CreateNextBookAsync`) and a **"Book N"** badge on the card (`NovelStatus.InSeries`/`SeriesSequence`). **The 5-phase roadmap is complete.**
- **Sources:** Google Docs, `.docx`, **RTF**, **ePub**, and **PDF**. `DocxTextExtractor`/`RtfTextExtractor`/`EpubTextExtractor` are pure-BCL in `Storyboarder.Domain/Text`; `PdfTextExtractor` (**PdfPig**, the added Infrastructure dep) reads PDF content streams. `GoogleDocsClient.ExtractorFor` routes by Drive mime type / extension (native Doc → Docs API, everything else → Drive byte-download + local extract). `ProjectService.VerifyAndHealOutputsAsync` runs at app start (`MainActivity`) to heal any "done" unit whose file went missing after a reboot.

### Secrets vault (cross-cutting)

Every app's keys and durable "magic strings" live in **ONE AES-256-GCM-encrypted file in the owner's Google Drive** (`storyworthtelling-secrets.json`), so the FocusPhone cutover's factory reset — which wipes every on-device store — no longer means re-entering every credential by hand. The vault types live in the shared **`Storyworthtelling.Voice`** library under the `Secrets/` folder (`Storyworthtelling.Voice.Secrets`), reusing its existing `IDriveTextFile`/`DriveTextFile` Drive seam: `SecretsVault` (a record with one section per app), `SecretsCrypto` (PBKDF2-SHA256 → AES-GCM, **BCL only**, no new dependency; a wrong passphrase fails the GCM tag as `WrongPassphraseException`), `SecretsEnvelope` (the on-Drive `{version,kdf,iterations,salt,nonce,ciphertext,tag}` shape), `ISecretsVaultStore`/`DriveSecretsVaultStore` (load returns a `SecretsVaultLoadResult` distinguishing Empty/Loaded/WrongPassphrase/Corrupt), and `SecretsVaultService` (the per-app orchestration: `LoadAsync` for restore, `PublishAsync(merge)` for a per-section save that never overwrites a vault it couldn't read). Fully unit-tested in `Storyworthtelling.Voice.Tests/Secrets/`. **Two-way, encrypted:** each app publishes its section on settings-save (and on connect/pair events — Ledger on a Plaid link, DailyLoader on a reMarkable register, Communication on Gmail save) and restores missing values on startup; the owner enters one **passphrase per app** (the single thing NOT in the vault — wiped by the reset, re-entered once, then unlocks the rest). The vault is the **single source of truth for the shared Claude key**, replacing the old plaintext `storyworthtelling-voice-config.json`: `VaultVoiceConfigStore` adapts the vault to the existing `IVoiceConfigStore` seam, so the voice stack is unchanged — MAUI apps swap the DI registration; the FocusPhone `VoiceGreeting`/`MusicTasteService` build it directly. Per-app wiring: MAUI apps add a `VaultPassphrase` to their settings store + a `VaultSync` helper + a restore hook in `MainActivity`; the FocusPhone native heads share `Codex.Ui.Voice.VaultPassphraseStore` + `SecretsVaultAccess` and restore in each head's launch Activity. **Ledger's per-bank Plaid access tokens** (generated on-device, in SQLite) are backed up via `AccountService.GetInstitutionCredentialsAsync`/`RestoreInstitutionsAsync` (unit-tested), so a reset restores every bank without re-linking. **Scope change:** writing the vault needs full `drive`, so Ledger + DailyLoader widen their token scope from `drive.readonly` to `drive` and FocusPhone's `VoiceGoogleAccount` does the same (the owner re-registers the scope; until then publish/restore degrade quietly and apps keep working from local settings). **Not yet done:** live-API verification on a real device (same as the Voice rollout).

**Vault passphrase field:** the one secret NOT in the vault, so every settings screen shows it **in the clear** (not a masked password field) — it must be read back and set identically in each app, and Android blocks clipboard copy on password-typed fields. (The Gmail app password and Plaid secret stay masked — those aren't the vault key.)

**Reading a key for tooling/automation (dev procedure, no secret stored here):** every shared credential already lives in the vault, so a build/automation step (e.g. the Gemini cover-paint pass) does not need a pasted key — it reads it from Drive. The vault file is `storyworthtelling-secrets.json` in the owner's Drive; decrypt it with the owner's **vault passphrase** (the only thing not stored, supplied at run time) using `Storyworthtelling.Voice.Secrets.SecretsCrypto` (PBKDF2-SHA256 → AES-256-GCM, envelope = `{Version,Kdf,Iterations,Salt,Nonce,Ciphertext,Tag}`), then read the section you need off the `SecretsVault` record: `Gemini.ApiKey`, `Claude.ApiKey`, `GitHubUpdateToken`, etc. The decrypted key is used in-process only — **never commit it, never put it in an artifact, doc, or log.** This is the streamlined path so future phases skip the "where's the key" runaround.

**Credential health → settings declutter (cross-cutting):** because the vault backs up and restores every key, a working key is a done state, not something to keep on screen. Shared, unit-tested types in **`Storyworthtelling.Voice`** under `Health/` (`Storyworthtelling.Voice.Health`): `CredentialHealth`/`CredentialHealthReport` (+ `CredentialHealthCodec` JSON), `AuthFailure.IsHttpCredentialRejection` (401/403, plus Gemini's HTTP-400 `API_KEY_INVALID`), `ICredentialHealthSink` (write seam), and `CredentialFieldState.Decide(isSet, health)` — the pure rule that a key field is shown **only** when it's missing or a live call with it was just rejected; a working key collapses to a "Working ✓" line with a **Replace** button. Each app's API clients report health at their HTTP choke point through an **optional** `ICredentialHealthSink` ctor param (default null, so existing client unit tests are untouched; DI injects it because `AddHttpClient` uses `ActivatorUtilities`), and a Preferences/SharedPreferences-backed `CredentialHealthStore` per head persists the report and is read by the settings screen. Only auth rejections flag a key — throttling/5xx/network are left alone so a blip never falsely reveals a field. Per-app credential ids + classifiers: Storyboarder (`claude`/`gemini`), Ledger (`plaid`, via `PlaidFailure` over Plaid `error_code` — item/token errors are a per-institution concern, not the shared credentials), DailyLoader (`nyt-api-key`/`nyt-cookie`/`remarkable`/`anthropic`), FocusPhone Communication (`gmail-app-password`, via MailKit `AuthenticationException` in `CommunicationSync`) and Launcher (`github-update-token`, via `GitHubReleaseClient`'s status-carrying exception in `UpdateService`). Ledger/DailyLoader `Infrastructure` gained a `Storyworthtelling.Voice` reference for the seam (DailyLoader bumped `Google.Apis.Auth` to 1.75.0 to match). Pure logic is unit-tested; the settings-screen wiring in the Android heads is compile-checked in CI, live-verify pending like the rest of the Voice/vault rollout.

### Ledger

An **Android (MAUI) app** that shows balances across your banks, credit cards, and loans in one place by connecting to the **Plaid** aggregator (no US consumer bank offers a per-user balance API directly). Modeled on Storyboarder/DailyLoader: an AndroidX **WorkManager** periodic worker refreshes each connected institution on-device (no web host, no backend), EF Core + SQLite stores the latest balances/liabilities, and a Paper & Ink list displays them. See `Ledger/`.

- Tests: `dotnet test Ledger/Ledger.Tests/Ledger.Tests.csproj -p:LedgerTfms=net10.0` (Domain + Infrastructure + Tests; no device, no keys — Plaid is faked via `FakeHttpMessageHandler`/Moq). The `-p:LedgerTfms=net10.0` switch builds Infrastructure for the desktop TFM only so the suite runs without the MAUI/Android workload.
- Android head (`Ledger.Android`, `net10.0-android`, app id `com.storyworthtelling.ledger`): build with the MAUI/Android workload + Android SDK (same minimal-SDK note as Storyboarder); signs with the shared repo keystore secrets. Background work uses `Xamarin.AndroidX.Work.Runtime` (daily `PeriodicWorkRequest` + a one-shot for "Refresh now").
- **Secrets & data model:** the Plaid **client id/secret + environment** are entered on the Settings page (stored in MAUI `Preferences`, read live by the worker via `LiveOptions<PlaidOptions>`); per-institution **access tokens** live in the SQLite DB (`Ledger.Domain.Model.Institution`). The DB is at `FileSystem.AppDataDirectory/ledger.db`. There is no backend by design — for a personal single-user app the credentials-in-Preferences tradeoff is accepted (see `Ledger/README.md`).
- **Connecting an account (net-new vs the other apps):** a "Connect an account" button opens **Plaid Hosted Link** in a `WebView` (`PlaidLinkPage`); the app creates the `link_token` and, on Done, reads the completed session's `public_token` via `/link/token/get`, exchanges it for an `access_token`, and records the `Institution`. This connect seam is the one piece to finalize against Plaid's current Hosted Link docs (redirect/session handling); everything after it (refresh → SQLite → display) is fully covered.
- **Data pulled:** `/accounts/balance/get` for every account, plus `/liabilities/get` (next payment due/amount + APR) for credit cards and mortgages. Auto/home-improvement loans and some credit unions may be unsupported by Plaid → fall back to manual awareness. The account list also shows the credit limit where Plaid reports one, and each account row **expands to recent transactions** loaded on demand from `/transactions/get` (last 30 days) — this is a UI-side fetch, not part of the background refresh, so no extra tables. Transactions is a Plaid **subscription product** (billed per Item in production; the link token requests it as the required `product` — Plaid rejects a link token with an empty products array — while `liabilities` goes in `required_if_supported_products` so deposit-only institutions still link).
- The launcher icon is **native** Android adaptive-icon resources under `Ledger.Android/Resources/mipmap-*`, generated by `Tools/IconStudio` (glyph `Glyphs.Ledger` — the four-plus-one ledger marks). Unlike the other apps, Ledger's generated icon binaries are **not committed**; the CI `build` job regenerates them with `dotnet run --project Tools/IconStudio` before building, and the same fatal **ICON CHECK** (`aapt2 dump badging`) proves the custom icon is in the APK. Design tokens are registered in DESIGN.md §16 with the usual leak-guard + parity tests.

EF migrations run against the desktop TFM: `LedgerTfms=net10.0 dotnet ef migrations add <Name> --project Ledger/Ledger.Infrastructure --framework net10.0` (a `DesignTimeDbContextFactory` supplies the context). ## Project Structure

Each project lives in a single `.sln` with multiple `.csproj` files — typically split by concern (e.g. `Domain`, `Infrastructure`, `API`, `Tests`). Keep projects coarse-grained until complexity actually demands splitting.

## Architecture Preferences

- Object-oriented; avoid functional-style abstractions that don't fit naturally in C#.
- Controllers handle HTTP; services handle logic; EF Core `DbContext` is the data access layer. Do not add a repository layer on top of `DbContext`.
- Do not access `DbContext` directly from controllers or above the service layer.
- Prefer fewer layers over more. Avoid redundant typecasts and pass-through classes that add no value.
- Use SignalR for pushing real-time updates to clients.
- Expose APIs via controllers with Swagger documentation.

## Code Style

Follow standard Microsoft C# naming conventions throughout. Do not use underscores in any identifier — this includes private fields (use `camelCase`, not `_camelCase`).

## Async

Use `async`/`await` only where I/O actually warrants it or where it will meaningfully improve expected performance. Do not make everything async by default.

## Error Handling

Handle errors where they occur. Propagate failures with a descriptive, specific message and preserve the stack trace for debugging. Do not swallow exceptions or replace them with vague messages.

## Testing

- Unit tests for all logic; integration tests at the API boundary.
- TDD strictly: tests are written before implementation.
- Do not skip or defer tests — untested code is not considered done.

## Dependencies

Only add a dependency if one of these is true:
1. It is already present in the project.
2. It is from Microsoft or another well-established, trusted publisher.
3. It is required to integrate with the specific tool or service being built.

When in doubt, implement it directly in C#.

## Git Workflow

- **Never push to `main`**. All changes go on a feature branch for review first.
- Open a pull request and wait for approval before merging.
