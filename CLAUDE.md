# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal projects repository — primarily background automation apps, with occasional MAUI mobile apps and Angular frontends. Projects are added incremenledger; update this file with project-specific build/test commands when a new one lands.

## Design

**`DESIGN.md` at the repo root is the Paper & Ink design bible** — the single source of truth for palette, typography, motion, materiality, spacing, components, PDF page specs, icon specs, voice, and accessibility across every project. Rules that matter when writing code:

- **No color hex or type-size literals outside the registered token files** (DESIGN.md §16). Leak-guard unit tests in every project enforce this; consume tokens instead (`Codex.Domain.Design.DesignTokens` + `Codex.Ui.Android` `PaperUi`/`PaperTheme` for FocusPhone, and the shared **`Storyworthtelling.Maui`** kit for the MAUI apps — Foreword has adopted it and so has no token file of its own; Ledger and Canonizer still carry `Storyboarder.Domain.Design.DesignTokens` + their own `Resources/Styles/DesignTokens.xaml` and adopt the kit at their own phases).
- The **eight** shared fonts live in `/Fonts` (Source Serif 4 — Regular, Semibold, Italic and **Black** — Source Sans 3 Regular and Semibold, Cascadia Code, and **Pinyon Script**, the calligraphy hand DESIGN.md §4 reserves for the owner's voice; static TTFs, OFL). Note that the FONT CHECK in `build-flyleaf.yml` and `build-post.yml` names only six of them, omitting Serif Black (every screen header) and Pinyon Script (the voice); `build-plate.yml` checks all eight. Native heads package them as assets via `Codex.Ui.Android`; MAUI heads via `<MauiFont>`; the Skia renderers via embedded resources (`EmbeddedTypefaces`).
- **Interaction rules are load-bearing** (DESIGN.md §5–§11): success is an inline state change (no success toasts/alerts), destructive acts are undo-first (an `UndoBar` window, not a confirm dialog), loading is a status sentence not a spinner, primary actions live in a pinned bottom bar, screens open with a Serif in-page header, time is 12-hour and list timestamps are relative (`RelativeTime`/`TimeFormats`, duplicated per Domain and kept identical by a parity test).
- **Generated artifacts** (icons, the paper-grain tile, the owner branding medallion) are all produced by the committed **`Tools/IconStudio`** console: `dotnet run --project Tools/IconStudio -- --repo-root .` (tests: `dotnet test Tools/IconStudio.sln`). Never hand-edit generated resources. **Owner photo swap:** drop a square image at `/Branding/owner.png` and rerun IconStudio — it circle-masks the photo into the medallion for every consumer (PDF covers + settings screens) and never clobbers an existing `owner.png`.
- **Owner's voice is pending** (DESIGN.md §11): the intent is to learn the owner's wit from their self-authored Google Drive docs, which needs the Google Drive connector authorized in claude.ai. Until then copy stays quiet-neutral.
- New projects start on-system: see DESIGN.md §15 for the MAUI/Angular defaults.

A **kill switch** (`MusicSettingsStore.ListeningGeniusEnabled`, on by default) + honest data note live on the Discovery screen; off clears the gathered history. **Discovery (Phase 7)** is a Music-menu entry: prompt-only playlists (`DiscoveryClient` → `PlaylistPlan` resolves ids to real tracks, dropping hallucinated ones) and a quiet weekly **"New for you"** shelf driven by a WorkManager `FridayPicksWorker` (`FridayPicksSchedule`, ISO-week gated) — no push, no badge. All model-agnostic logic is unit-tested; the Android heads (recording hook, `MusicTasteService`, the Friday worker) are device-gated and compile-checked in CI. Live-API + on-device verification pending, like the Voice rollout.
- **Podcast bulk mark-played + Drive library backup:** long-pressing an episode opens a Paper action sheet (**Mark played** / **Mark older as played** — clears every same-show episode published before it), and long-pressing a show on the shelf offers **Mark all as played**; the id selection is the pure, unit-tested `BulkListen` and both bulk paths mark through an undo-aware batch that restores only the ids it newly added. The audio library — subscriptions + listened + resume positions, **plus the per-show playback speed/skip-silence settings and the equalizer curve/presets/loudness** — now also **backs up to Drive** as one plaintext JSON file (`focusphone-audio-library.json`, `DriveAudioLibraryStore` over the shared `IDriveTextFile` seam) so a factory reset or new phone restores what you follow, what you've heard, and how you tuned playback. The `AudioLibrarySnapshot` carries all of it (settings + EQ are optional so an older backup still round-trips), and its `ContentEquals` is structural over the dictionaries/lists so an unchanged library skips the Drive write; `PlaybackSettingsSnapshot` moved from Infrastructure to `Domain/Audio` so the Domain snapshot can hold it (codec stays in Infrastructure, matching the other podcast types). EQ band gains are hardware-shaped but restore safely across devices — `EqualizerActivity` adopts a stored curve only when the band count matches and `AudioEffects` applies the overlap. The phone is the **single writer** (a future Wear OS app reads through the phone, not Drive), so it's a one-writer mirror not a CRDT: the pure `AudioLibrarySync.Decide` says local wins while it has shows (so an unsubscribe propagates instead of being resurrected) and Drive only repopulates a device with **no** subscriptions. `PodcastLibrarySync` (Android) carries the verdict out between the SharedPreferences stores and Drive — restore on launch when the device is fresh, backup on `OnPause` of the home, Manage, and Equalizer screens. Reuses the Audio head's existing full-`drive` scope; best-effort and not yet live-verified, like the rest of the Drive rollout.
- **Podcast fetch speed (cold-start cache + parallel refresh):** episodes were never persisted — every launch rebuilt them in-memory and opened on a blank "Fetching episodes…" while feeds fetched **sequentially** (N shows = N serial round-trips). Now the last fetch is cached on-device (`EpisodeCacheStore` prefs → `PodcastCache` domain record + unit-tested `PodcastCacheCodec`) and `LoadCachedEpisodes` paints the shelf instantly on launch; `RefreshFeedsAsync` then refreshes **all feeds concurrently** (`Task.WhenAll` over `FetchFeedAsync`, wall time = the slowest feed) in the background and updates the shelf in place. The refresh is **cache-preserving**: it starts from the cached episodes pruned to still-subscribed feeds and only replaces feeds that fetched successfully, so a flaky network keeps a show's last-known episodes instead of dropping it; per-feed failures are summarized in one toast rather than a wall of them. The cache is purely local (episodes are re-derivable from feeds — deliberately excluded from the Drive backup above).
- **Music scan (incremental + bounded-parallel):** the Music side already loads its catalog from a local SQLite cache (`MusicCatalogCache`) on launch, so browse is instant/offline; the slow part was the scan, which cleared the cache and re-read every file's tags **sequentially** over Drive. Now `MusicScanner` is **incremental**: it diffs the Drive listing against the cache's stored per-file change signature (modified-time + size — new `modifiedTimeTicks`/`sizeBytes` columns, added to old caches by an in-place `ALTER TABLE` migration) via the pure, unit-tested `MusicScanPlan.Compute`, then only re-reads new/changed files and deletes tracks whose file is gone (no more clear-and-rebuild). The tag reads run in **bounded-parallel batches** (`MaxConcurrentReads = 8`, `Task.Run` + `Task.WhenAll`) — bounded to respect the Drive quota/mobile radio and because `MusicCatalogCache` is a single `SqliteConnection` (not safe for concurrent writes), so each batch of parallel reads lands in **one serialized transaction** (the versioned `Upsert` overload). Progress is reported over the files actually being read, so a rescan that changed little finishes fast. `MusicScanPlan` + the cache versioning are unit-tested; the scanner's Android wiring is compile-checked in CI.

### Streaming (Score, decided WS2)

**TIDAL is the provider.** Chosen after a five-service survey (P6 WS2) on one criterion: it is the only service whose Android SDK lets Score **be the player**. Spotify's App Remote and a YouTube-Music WebView both make Score a *remote control* for someone else's player, which cannot satisfy the standing **merged-library** rule (owned Drive files and streamed tracks indistinguishable, in one queue, one media session, one listening log). Also ruled out: Spotify deprecated `/audio-features` (tempo) in Nov 2024 and caps Development Mode at 5 users on Premium; Google has blocked OAuth in embedded WebViews since July 2023 (`disallowed_useragent`), so a WebView cannot even sign in; Apple's Android MusicKit SDK has not been updated since Dec 2021; Qobuz is partner-only.

- **Account:** one **shared** TIDAL account for both people, so its credentials live in the **shared** vault section — `SecretsVault.Tidal` (`ClientId`/`ClientSecret`/`RefreshToken`; the refresh token is the reset-survival credential, mirroring `RemarkableSecrets.DeviceToken`). **Watch:** an Individual plan permits **one concurrent stream**, so two people listening at once will fight; Family ($19.99) is the fix if that bites.
- **Constraint to honour:** playback must go through an unmodified official **TIDAL Player module** — that is the only sanctioned route, and TIDAL rejects quota requests that work around it. Player + Offline engines both live in the Kotlin SDK, so B7 needs a **Xamarin binding project** (precedent: `Codex.GmBridge.Binding`).
- **Not from TIDAL:** lyrics come from **LRCLIB** (free, keyless, ~3M time-synced LRC) and tempo from **tag BPM → Deezer's keyless `bpm`** → DSP as a last resort. Both are service-independent, so they work for owned files too and do not wait on B7.
- **Unverified:** whether the Player SDK pulls in Play Services, and whether TIDAL's lyrics resource carries timings. Both need a spike before B7 is scheduled.
- **Before committing (revised after inspecting Drive, 24 Aug):** the Takeout is already in Drive — thirteen split `Takeout/YouTube and YouTube Music/music (library and uploads)/` folders — and it landed as **real audio**, not just metadata. Sampling shows it is exactly the irreplaceable half (acoustic, live and session recordings that were never on a streaming catalogue) and that the files are **fully ID3-tagged** (TIT2/TALB/TPE1/TPE2/TRCK/TYER/TCON), which is what Score's tag-driven scanner needs — so the long tail is already safe and already organizable, and no licensed service was ever going to carry it. `DriveMusicClient` walks folders breadth-first, so the split structure scans fine **provided the chosen music folder sits above the Takeout folders** — worth confirming, since a folder chosen before the Takeout landed would miss all of it. Two caveats: the Takeout's **metadata CSVs are not in Drive** (no `music-library-songs.csv` anywhere), so there is no record of library entries that were streaming-catalogue only — a fresh Takeout of just the CSVs would recover that list if it matters; and `(1)`/`(2)`-suffixed filenames suggest repeated downloads, so expect duplicates in the scanned library. What remains for the coverage check is therefore only **mainstream catalogue**, where TIDAL's 110M is not in doubt.

### Canonizer (project folder `Storyboarder/`, namespaces `Storyboarder.*`)

An **Android (MAUI) app** — user-facing name **Canonizer** — that reads a novel manuscript and produces a **revision report** as its star product, with **one wordless image per scene as supporting evidence** (a fidelity check: does the beat land visually as written?). It pivoted from a graphic-novel factory ("Storyboarder"); the **internal identity is deliberately unchanged** (namespaces `Storyboarder.*`, solution, `StoryboarderDbContext`, `storyboarder.db`, app id `com.storyworthtelling.storyboarder`) so an installed build upgrades in place — only the user-facing name, the icon (a **red pen nib**), and some domain concepts changed. Four **load-bearing principles**: **nudge never write** (diagnose & point, never ghost-write prose/lines) · **both ends of the pendulum** (flag under- *and* over-writing) · **the report is the star** (the image is evidence) · **quiet by default** (silent Drive delivery, one in-app note, no push/toast). Pipeline (all state in the DB, one unit of work per worker cycle, resumable): `Ingesting` → `BuildingDesignBible` (per-chunk analysis + reference sheets on the **strong** Claude model) → `RenderingSceneImages` (one wordless portrait per scene) → `ComposingAnalysis` (map-reduce the manuscript into the report — a **story half** and a **craft half**, two Claude calls persisted separately because one reply can't carry both, plus a separate resumable **voice-consistency** call `AssessVoiceConsistency`; rendered to raster pages via SkiaSharp and wrapped by the image-based PDF composer) → `Archiving` (deliver to Drive) → `Completed`. Modeled on Foreword: an AndroidX **WorkManager** periodic worker drains the pipeline on-device (no web host, no SignalR). See `Storyboarder/`.

- **Series awareness (Phase 5, cross-book continuity):** links related **books** so a sequel reuses the prior book's canon. Three reuse mechanisms: (1) **returning-entity image reuse** — `ReviewProcessor.CarryForwardSeriesEntities` (folded into `ConsolidateBible`, the book-level mirror of `CarryForwardScenes`) copies a returning character/place's rendered reference image from the prior book (matched by name/alias, kind-scoped) so it stays visually on-model, keeping this book's own description; (2) the **Series continuity read** — a resumable `ComposeAnalysis` sub-step **2f** (gated by `BookAnalysis.SeriesContinuityJson` + `PreviousBookId`, billed once like the other reduce halves) runs a new **`IClaudeAnalysisClient.AssessSeriesContinuity`** call over a **`SeriesCanon`** (`Domain/Analysis/SeriesModels.cs` — the prior book's cast/settings, final `ContinuitySummary`, and open finding threads) built by `LoadSeriesCanon`/`LoadOpenThreads`, returning a **`SeriesContinuity`** (`SeriesBreak`s = contradictions of prior canon; `CarriedThread`s = prior open threads tagged Addressed/Ignored/Contradicted), graceful-empty like `ProposeExpansion`; (3) **carried findings** — the prior book's open threads are surfaced through that read (a problem spanning books, tracked), leaving the per-draft finding reconciliation untouched. Folded into the report via `WithSeriesContinuity`; `AnalysisDocumentRenderer.RenderSeriesContinuity` adds a **"Series continuity"** section (after voice consistency) that stays **silent** for a standalone book or a clean sequel (quiet by default), mirrored through `GetReportAsync`. ### Vector documents (cross-cutting)

Every document in the suite was a **150-DPI PNG per page** wrapped by PdfSharp — a picture of a page: nothing selectable or searchable, roughly ten times the bytes on a full page, and resampled twice on e-ink, which is what made small type look soft. **`Storyworthtelling.Paper/VectorPdfSink`** sends the same Skia draw calls to `SKDocument.CreatePdf` instead of a bitmap, so text stays text and fonts are embedded. Foreword's `SkiaPageLayout` draws through it; the draw calls were unchanged by the move, since a PDF's user space is already points — the raster path only scaled because a bitmap has pixels.

**The size claim is reproduced in a test rather than cited**, and the first version of that test failed for the right reason: on a nearly blank page the vector PDF is *larger* (75,700 bytes against 17,442), because a PDF embeds its fonts as a fixed ~75 KB cost while an almost-white PNG compresses to nothing. On five realistic pages it measures **162,075 vector against 1,656,186 raster** (~10×), and a second test pins the mechanism — five pages cost less than twice one, because the fonts are embedded once. Tests read the PDF back with **PdfPig** (the reader Canonizer already uses) and assert the text is extractable, that images survive on a vector page (D5), and that the pages still merge with the NYT crossword PDF through PdfSharp.

**`PaperTypeScale`** is the printed ladder — the screen ladder at a registered `Ratio` of 0.75 (D30, DESIGN.md §19) — replacing eight ad-hoc point sizes across the composers, with a guard that no composer picks a size or names an `SKColors.*` instead of a Paper & Ink role. The ground is the one exempted colour: the sheets stay white for the newspaper look, a standing decision rather than an oversight.

### The MAUI kit (cross-cutting)

A shared **`Storyworthtelling.Maui`** library (repo root, own `.csproj` + `.Tests`) carries the Paper & Ink role table, the component styles and the eight fonts for the MAUI heads — the counterpart of `Codex.Ui.Android`'s `PaperUi`/`PaperTheme`, which had no MAUI equivalent. Pieces: `Resources/Styles/Paper.xaml` (a **registered token file**, DESIGN.md §19, carrying an `x:Class` so a head can merge it — a XAML `Source=` resolves only inside its own assembly, so heads do `Resources.MergedDictionaries.Add(new PaperKit())` in `App.xaml.cs`), and `PaperFonts.Register` (passed straight to `ConfigureFonts`).

**It exists because the design system was written twice and enforced once.** Each MAUI head kept a private copy of the palette and a leak-guard test holding a *second* hand-typed copy to check it against, so both could be wrong together — and were. Four live bugs came out of the first parity run against `PaperColorTokens`: the accent was still the **retired terracotta** (`#C2542F`) rather than the Action role's pine, **Display** drew in Serif Semibold where DESIGN.md §4 gives every screen header Serif **Black**, the **Label** role took the full ink instead of the muted one, and the **owner's voice had no style at all**. The last two share a cause worth remembering: `SourceSerif4-Black.ttf` and `PinyonScript-Regular.ttf` shipped inside every APK with **no alias registered**, and an unregistered family is not an error in MAUI — the platform substitutes the system face and says nothing.

**The pure halves are pulled out and tested for real.** `Layout/BinderTabLayout` and
`DesignTokens` (Space + Shape only — type sizes stay in the registered `Paper.xaml`) are copies of
`Codex.Domain`'s, kept identical by a **source-level** parity guard rather than by a test that
restates a few remembered values. `State/DogEarState` is new: DESIGN.md §13's rule that an undo
**outranks** a waiting notice and hands the corner back when its window closes had only ever existed
inside the native view, tangled with the host layout, a weak table and a `Handler`, so nothing tested
it. It is now a decision with time passed in. The test project compiles those files directly
(`<Compile Include="..\Storyworthtelling.Maui\...">`), so the real types are exercised — the kit's
own TFM makes a project reference impossible.

**The components** are the binder tab strip, the dog-ear, list rows with the §7 checkbox, and the
accordion picker; the status line and card groups are styles in the dictionary. The strip is the *native*
shape by decision — a glyph over a horizontal label filling the 66dp gutter, the same component
Score and Post draw — so all five apps reach for one divider; `BinderArea` carries **two** glyph
sources rather than one tinted at runtime, because MAUI has no equivalent of Android's
`SetColorFilter` and the only ready answer is a toolkit dependency. The dog-ear is Post's `FoldView`
geometry member for member (two triangles: the **hole** showing what the fold carries, and the
**flap**, the corner turned over and lying back across the page), painted through a `GraphicsView`
`IDrawable`; `DogEarState` decides, the view paints and owns the clock — the state takes time as an
argument, which is what makes it testable. Every view reads its tokens through
**`PaperResources.Token`**, one place because the rule is easy to get subtly wrong: a
`ResourceDictionary`'s indexer looks only at its own entries while `TryGetValue` walks what has been
merged in, so the indexer appears to work until the kit is the only source left. The **wash** tier
lives in the dictionary as 8-digit ARGB and the palette guard *composes* it from the role's mark and
`PaperColorTokens.WashAlpha` rather than trusting the digits.

The kit is `net10.0-android`, so `build-shared-libs` can only run its **tests**; its compilation is proven by the heads that reference it, which is why `Storyworthtelling.Maui/**` is in `build-android.yml`'s path filter and why the guards read files rather than load types. Tests: `dotnet test Storyworthtelling.Maui.Tests/Storyworthtelling.Maui.Tests.csproj` — palette against `PaperColorTokens` **by reflection**, the type ladder against `Codex.Domain`'s own source file, every `FontFamily` against what `PaperFonts` registers, the nine roles' faces and inks, Serif Italic's single role, no letterspacing, buttons at Label size. **Not yet verified:** no screen drawn from the kit has been opened on a device.

### Self-update (cross-cutting)

A shared **`Storyworthtelling.Updates`** library (repo root, own `.csproj` + `.Tests`, `net10.0`, pure .NET) owns the decisions behind the rolling **`apps-latest`** GitHub release channel, extracted from Flyleaf's `UpdateService` — which had been the only implementation and so the only place the rules existed. Pieces: `InstallCandidate`, `SuiteApps` (the `com.storyworthtelling.` prefix that is the channel's whole trust boundary), `SiblingUpdatePlan`, `UpdateRunResult`/`AppInstallResult`/`InstallOutcome`/`InstallOutcomes`, and **`UpdateScope.Decide(role, selfPackage, …)`**. `Codex.Domain`'s `PolicyContext.OwnerPackagePrefix` keeps its own copy so Domain stays dependency-free, kept identical by a `FrozenInvariantsTests` parity guard.

**`UpdateScope.Decide(role, selfPackage, …)` answers "which of this release's APKs do *I* install?", and the answer depends on the device rather than the app.** `Custodian` installs for the whole suite — newer or not-yet-installed — and is what **Flyleaf** does on the locked phone, because as device owner it is the only thing that can install silently at all (`ApkInstaller` is device-owner-only and `NoInstallUnknownSources` stays on). `SelfOnly` keeps just the running app current, and is for an **unrestricted** phone where each app can run the confirmed installer itself (Jordan's install, B8). **Decided deliberately:** the launcher stays the single point of failure for updates on the locked phone rather than opening an exported install service on it — the lockdown's install restriction is worth more than the redundancy. Both roles gate on the owner namespace first, which is never a device question.

### Secrets vault (cross-cutting)

Every app's keys and durable "magic strings" live in **ONE AES-256-GCM-encrypted file in the owner's Google Drive** (`storyworthtelling-secrets.json`), so the FocusPhone cutover's factory reset — which wipes every on-device store — no longer means re-entering every credential by hand. The vault types live in the shared **`Storyworthtelling.Voice`** library under the `Secrets/` folder (`Storyworthtelling.Voice.Secrets`), reusing its existing `IDriveTextFile`/`DriveTextFile` Drive seam: `SecretsVault` (a record with one section per app), `SecretsCrypto` (PBKDF2-SHA256 → AES-GCM, **BCL only**, no new dependency; a wrong passphrase fails the GCM tag as `WrongPassphraseException`), `SecretsEnvelope` (the on-Drive `{version,kdf,iterations,salt,nonce,ciphertext,tag}` shape), `ISecretsVaultStore`/`DriveSecretsVaultStore` (load returns a `SecretsVaultLoadResult` distinguishing Empty/Loaded/WrongPassphrase/Corrupt), and `SecretsVaultService` (the per-app orchestration: `LoadAsync` for restore, `PublishAsync(merge)` for a per-section save that never overwrites a vault it couldn't read). Fully unit-tested in `Storyworthtelling.Voice.Tests/Secrets/`. **Two-way, encrypted:** each app publishes its section on settings-save (and on connect/pair events — Ledger on a Plaid link, Foreword on a reMarkable register, Post on mail settings save) and restores missing values on startup; the owner enters one **passphrase per app** (the single thing NOT in the vault — wiped by the reset, re-entered once, then unlocks the rest). The vault is the **single source of truth for the shared Claude key**, replacing the old plaintext `storyworthtelling-voice-config.json`: `VaultVoiceConfigStore` adapts the vault to the existing `IVoiceConfigStore` seam, so the voice stack is unchanged — MAUI apps swap the DI registration; the FocusPhone `VoiceGreeting`/`MusicTasteService` build it directly. Per-app wiring: MAUI apps add a `VaultPassphrase` to their settings store + a `VaultSync` helper + a restore hook in `MainActivity`; the FocusPhone native heads share `Codex.Ui.Voice.VaultPassphraseStore` + `SecretsVaultAccess` and restore in each head's launch Activity. **Ledger's per-bank Plaid access tokens** (generated on-device, in SQLite) are backed up via `AccountService.GetInstitutionCredentialsAsync`/`RestoreInstitutionsAsync` (unit-tested), so a reset restores every bank without re-linking. **Scope change:** writing the vault needs full `drive`, so Ledger + Foreword widen their token scope from `drive.readonly` to `drive` and FocusPhone's `VoiceGoogleAccount` does the same (the owner re-registers the scope; until then publish/restore degrade quietly and apps keep working from local settings). **Not yet done:** live-API verification on a real device (same as the Voice rollout).

**Vault passphrase field:** the one secret NOT in the vault, so every settings screen shows it **in the clear** (not a masked password field) — it must be read back and set identically in each app, and Android blocks clipboard copy on password-typed fields. (The Gmail app password and Plaid secret stay masked — those aren't the vault key.)

**Reading a key for tooling/automation (dev procedure, no secret stored here):** every shared credential already lives in the vault, so a build/automation step (e.g. the Gemini cover-paint pass) does not need a pasted key — it reads it from Drive. The vault file is `storyworthtelling-secrets.json` in the owner's Drive; decrypt it with the owner's **vault passphrase** (the only thing not stored, supplied at run time) using `Storyworthtelling.Voice.Secrets.SecretsCrypto` (PBKDF2-SHA256 → AES-256-GCM, envelope = `{Version,Kdf,Iterations,Salt,Nonce,Ciphertext,Tag}`), then read the section you need off the `SecretsVault` record: `Gemini.ApiKey`, `Claude.ApiKey`, `GitHubUpdateToken`, etc. The decrypted key is used in-process only — **never commit it, never put it in an artifact, doc, or log.** This is the streamlined path so future phases skip the "where's the key" runaround.

**Credential health → settings declutter (cross-cutting):** because the vault backs up and restores every key, a working key is a done state, not something to keep on screen. Shared, unit-tested types in **`Storyworthtelling.Voice`** under `Health/` (`Storyworthtelling.Voice.Health`): `CredentialHealth`/`CredentialHealthReport` (+ `CredentialHealthCodec` JSON), `AuthFailure.IsHttpCredentialRejection` (401/403, plus Gemini's HTTP-400 `API_KEY_INVALID`), `ICredentialHealthSink` (write seam), and `CredentialFieldState.Decide(isSet, health)` — the pure rule that a key field is shown **only** when it's missing or a live call with it was just rejected; a working key collapses to a "Working ✓" line with a **Replace** button. Each app's API clients report health at their HTTP choke point through an **optional** `ICredentialHealthSink` ctor param (default null, so existing client unit tests are untouched; DI injects it because `AddHttpClient` uses `ActivatorUtilities`), and a Preferences/SharedPreferences-backed `CredentialHealthStore` per head persists the report and is read by the settings screen. Only auth rejections flag a key — throttling/5xx/network are left alone so a blip never falsely reveals a field. Per-app credential ids + classifiers: Storyboarder (`claude`/`gemini`), Ledger (`plaid`, via `PlaidFailure` over Plaid `error_code` — item/token errors are a per-institution concern, not the shared credentials), Foreword (`nyt-api-key`/`nyt-cookie`/`remarkable`/`anthropic`), Post (`gmail-app-password` on the IMAP path and `gmail-account` on the Gmail API one; ids now live in `Codex.Domain/Credentials/CredentialIds.cs` so a client and a settings screen share them rather than each holding a copy) and Launcher (`github-update-token`, via `GitHubReleaseClient`'s status-carrying exception in `UpdateService`). Ledger/Foreword `Infrastructure` gained a `Storyworthtelling.Voice` reference for the seam (Foreword bumped `Google.Apis.Auth` to 1.75.0 to match). Pure logic is unit-tested; the settings-screen wiring in the Android heads is compile-checked in CI, live-verify pending like the rest of the Voice/vault rollout.

### Ledger

An **Android (MAUI) app** that shows balances across your banks, credit cards, and loans in one place by connecting to the **Plaid** aggregator (no US consumer bank offers a per-user balance API directly). Modeled on Storyboarder/Foreword: an AndroidX **WorkManager** periodic worker refreshes each connected institution on-device (no web host, no backend), EF Core + SQLite stores the latest balances/liabilities, and a Paper & Ink list displays them. See `Ledger/`.

- Tests: `dotnet test Ledger/Ledger.Tests/Ledger.Tests.csproj -p:LedgerTfms=net10.0` (Domain + Infrastructure + Tests; no device, no keys — Plaid is faked via `FakeHttpMessageHandler`/Moq). The `-p:LedgerTfms=net10.0` switch builds Infrastructure for the desktop TFM only so the suite runs without the MAUI/Android workload.
- Android head (`Ledger.Android`, `net10.0-android`, app id `com.storyworthtelling.ledger`): build with the MAUI/Android workload + Android SDK (same minimal-SDK note as Storyboarder); signs with the shared repo keystore secrets. Background work uses `Xamarin.AndroidX.Work.Runtime` (daily `PeriodicWorkRequest` + a one-shot for "Refresh now").
- **Secrets & data model:** the Plaid **client id/secret + environment** are entered on the Settings page (stored in MAUI `Preferences`, read live by the worker via `LiveOptions<PlaidOptions>`); per-institution **access tokens** live in the SQLite DB (`Ledger.Domain.Model.Institution`). The DB is at `FileSystem.AppDataDirectory/ledger.db`. There is no backend by design — for a personal single-user app the credentials-in-Preferences tradeoff is accepted (see `Ledger/README.md`).
- **Connecting an account (net-new vs the other apps):** a "Connect an account" button opens **Plaid Hosted Link** in a `WebView` (`PlaidLinkPage`); the app creates the `link_token` and, on Done, reads the completed session's `public_token` via `/link/token/get`, exchanges it for an `access_token`, and records the `Institution`. This connect seam is the one piece to finalize against Plaid's current Hosted Link docs (redirect/session handling); everything after it (refresh → SQLite → display) is fully covered.
- **Data pulled:** `/accounts/balance/get` for every account, plus `/liabilities/get` (next payment due/amount + APR) for credit cards and mortgages. Auto/home-improvement loans and some credit unions may be unsupported by Plaid → fall back to manual awareness. The account list also shows the credit limit where Plaid reports one, and each account row **expands to recent transactions** loaded on demand from `/transactions/get` (last 30 days) — this is a UI-side fetch, not part of the background refresh, so no extra tables. Transactions is a Plaid **subscription product** (billed per Item in production; the link token requests it as the required `product` — Plaid rejects a link token with an empty products array — while `liabilities` goes in `required_if_supported_products` so deposit-only institutions still link).

Unlike the other apps, Ledger's generated icon binaries are **not committed**; the CI `build` job regenerates them with `dotnet run --project Tools/IconStudio` before building, and the same fatal **ICON CHECK** (`aapt2 dump badging`) proves the custom icon is in the APK. EF migrations run against the desktop TFM: `LedgerTfms=net10.0 dotnet ef migrations add <Name> --project Ledger/Ledger.Infrastructure --framework net10.0` (a `DesignTimeDbContextFactory` supplies the context). APK builds in CI via `.github/workflows/build-ledger.yml`.

### Foreword (project folder `Foreword/`, namespaces `Foreword.*`)

An **Android (MAUI) app** — user-facing name **Foreword**, formerly DailyLoader — that builds a
morning brief and delivers it to the owner's reMarkable tablet before they wake, then reads
hand-written notes back into Google Calendar/Tasks. P9 renames it and rebuilds it around three
documents (The Day, The Brief, Prayer). Gate deliverables live in the project folder:
`FOREWORD-P9-TECHNICAL-FINDING.md` (approved) and `FOREWORD-P9-PLAN.md`.

**The mockups are the specification** and every UI or renderer task builds from them 1:1,
surfacing anything that cannot be built as drawn rather than substituting:
`https://claude.ai/code/artifact/6bb65b0d-04da-47f3-bf72-a04020217e0c`

- **Checking a MAUI member without the workload.** The Android head cannot be compiled here, so CI
  was finding one API mistake per round — `DatePicker.Date` and `DateChangedEventArgs.NewDate` are
  `DateTime?`, and `Grid` has *both* a static `SetColumn(BindableObject, int)` and an instance
  `SetColumn(IView, int)`, so the unqualified call binds to the instance one and will not compile
  from a static context. The signatures can be read locally instead: pull
  `Microsoft.Maui.Controls.Core`, `Microsoft.Maui.Core` and `Microsoft.Maui.Graphics` from nuget.org
  (flat-container URLs), unzip them, and reflect over `lib/net10.0-android*/` with a
  `MetadataLoadContext` — the runtime directory (`dotnet --list-runtimes`) has to be in the resolver
  path, and `Microsoft.Maui.Controls` itself is a metapackage carrying no assemblies. That is the
  standing "read member names out of the package's own metadata" rule, made possible for this head.
- Tests: `dotnet test Foreword/Foreword.Tests/Foreword.Tests.csproj -p:ForewordTfms=net10.0`
  (the switch builds Infrastructure for the desktop TFM only, so the suite runs without the
  MAUI/Android workload). The Android head cannot be compiled in a network-restricted sandbox —
  CI is its only compiler, which is why the guards below read the repo by content rather than
  relying on the build.
- APK builds in CI via `.github/workflows/build-android.yml`; artifact **Foreword-Android**.
  versionCode is **band 7** of the shared formula (see Self-update above) — chosen to clear
  DailyLoader's old ~609,000,000 timestamp codes so the app upgrades **in place**. The band is
  not the version the owner sees: the display version is **2.0.x** (`2.0.<run_number>`, injected by
  the workflow), which is the string the Settings foot line prints. The mockups draw it as
  `Foreword 2.0.512 · com.storyworthtelling.dailyloader`, and a guard keeps the csproj and the
  workflow on that line — a build stamp there would be monotonic but unreadable.
- **The calendar page (P9 Release D)** is the owner's top priority and carried two live bugs with
  one cause. `WorkScheduleAugmenter` **appends** the synthetic nine-to-five to the day's events, so
  it drew last — an opaque box over every meeting inside it (**B3**); overlapping events had no
  collision detection at all, so the later one painted over the earlier (**B2**). `EventLanes`
  (pure, `Foreword.Domain/Calendar`) decides both: overlapping events share the column by lane, a
  work block is a **container** drawn first and taking no lane, and anything past
  `LegibleLanes = 2` falls to an **Also today** list under the grid rather than being squeezed to a
  three-character box. `CalendarEvent.Column` became **`Columns`, a set** (**D31**), resolved from
  guests → every name in the title → nobody-named-on-a-shared-calendar-means-everybody;
  `SharedEventMode` picks between one spanning box and a box per column with a "with …" line
  (**D32**). An **unmapped** calendar is held and named on the page (**D34**); one the owner
  answered with "not printed" is dropped silently, which is the difference between them.
  **`CalendarMappingCodec` is the one place the stored shape is decided** — it must register
  `JsonStringEnumConverter`, because every column in every document already on a phone is the word
  "Rowan", never the number 0, and the vault carries a copy of that document under a frozen key.
- **The rename froze five things, and every one of them is invisible** — nothing fails at build
  time if they move, and nothing fails loudly at run time either; the app just quietly stops
  delivering, or comes up with empty settings. `Foreword.Tests/Guard/ForewordInvariantsTests.cs`
  is what fails instead:
  - **`ForewordIdentity.ApplicationId` = `com.storyworthtelling.dailyloader`**, in one constant.
    A device recognises an update only when the package name is unchanged, and the channel
    installs by package id. It is the app's address, not a description.
  - **`DeliveryWorker`'s registered Java name.** `Schedule` enqueues unique periodic work with
    `ExistingPeriodicWorkPolicy.Keep`, so a phone that already has work scheduled keeps a row
    naming this class; move it and WorkManager fails to instantiate a class that no longer
    exists and the mornings simply stop. Built from the frozen constant, so it still reads
    `…dailyloader.DeliveryWorker` inside an app that says Foreword everywhere else.
  - **The unique work name `crossword-delivery`**, persisted beside it — change it and the old
    work is never replaced, so the phone runs two schedules or none.
  - **`MainActivity`'s Java name**, which previously had none (it was generated from the
    namespace, so the rename would have moved it).
  - **The nine `PreferenceKeys`**, which were `nameof(TheProperty)` — tidy-looking and a trap,
    since renaming a property renames its key and the stored value is not migrated or reported,
    just not found. The constants' values are the old property names, so no phone notices.
- **The secrets vault section is `SecretsVault.Foreword` in code and `"DailyLoader"` on the
  wire** (`[JsonPropertyName]`). The vault has no naming policy, so a property name *is* the key
  written to the owner's Drive; renaming it plainly would have made every existing vault
  deserialise the section to its empty default, silently, losing the Anthropic key and the
  calendar mapping JSON. Guarded by `VaultWireNamesTests`, whose load-bearing case is written as
  the file actually on Drive rather than as a round trip — a round trip alone passes happily with
  the section renamed at both ends, which is precisely the bug.
- The launcher icon is **native** adaptive-icon resources under `Foreword.Android/Resources/mipmap-*`,
  generated by `Tools/IconStudio` (spec `Foreword`, glyph `Glyphs.FoldedPaper`, resource name
  `ic_launcher` — frozen, since `[Application(Icon=…)]` names it). Never hand-edit them.
- `.github/workflows/generate-keystore.yml` still says `CN=DailyLoader`, deliberately: it is the
  one keystore every `com.storyworthtelling` app signs with, and the certificate already issued
  carries that name.
- **Prayer is isolated by a type, not by care (D15, Release H).** `Foreword.Domain/Prayer/PrayerText`
  is what the owner writes on the prayer page, and the only way to read it is to declare yourself an
  `IPrayerReader` — of which there are **five**, enumerated by `PrayerIsolationTests`: the vision
  transcriber, the pastoral composer, the archive codec's caller, the pages that print it, and the
  rotations editor on the phone. The reflective half of that guard can only see Domain and
  Infrastructure, so a second, **source-level** half scans the Android head too; a sixth reader is a
  decision, not a diff. `ToString()` returns a redaction because interpolation is the one hole a type
  cannot close — C# calls it for you with no cast and no warning. The three public composers (the
  brief's opening, the calendar's narrator, the checklist's coach) take and return **strings**, which
  is what makes "the journal cannot reach them" structural. What *private* does not mean, stated at
  gate 1 and accepted: the page is transcribed, so a vision model reads it. What it means is that
  nothing from it reaches Google Tasks, the calendar, the voice profile, or any shared file.
- **The prayer archive is the only copy, and it is encrypted.** One Drive file
  (`storyworthtelling-prayer-archive.json`) through the shared `Storyworthtelling.Voice`
  `VaultEnvelope` — now **public** rather than copied, since there are three such files — locked with
  the same passphrase the vault uses. The journal page is trashed off the tablet once transcribed, so
  `DrivePrayerArchive.SaveAsync` **reads the file back first and refuses** (`PrayerArchiveLockedException`)
  rather than writing over something it could not decrypt; `PrayerDeliveryService` orders the morning
  read → fold → compose → upload → save → trash so that every step which can fail does so *before*
  the sheet is thrown away. Encryption over plaintext was the owner's decision, cost accepted: lose
  the passphrase and the archive is gone.
- **How something gets onto the prayer list — both ways, by the owner's decision.** A one-off request
  is **written** on the journal page, under an "Add to the list" strip at its foot; a standing list
  prayed through one a day (a missionary list) is **edited on the phone** (`RotationsPage` /
  `RotationEditPage`, neither in the approved mockup set — the idea arrived with the answer).
  `JournalRegions` is the one place the two writable bands' coordinates live, and both the painter and
  the transcription prompt read them from it: a line under the strip becomes a printed request and the
  same line two inches higher stays private, so a disagreement about that boundary would put a private
  thought on a printed page. `RotationPick` is **arithmetic on the date, never a stored cursor** — a
  cursor advances on a morning that never delivered, so a name is skipped and nobody finds out.
- **Nothing is hardcoded to one person (Release I).** Foreword had only ever run on one phone, so one
  person was the answer to three questions nobody had noticed were questions: what a `CalendarEvent`'s
  columns start as, what `CalendarMappingOptions.DefaultColumn` is, and where a hand-written note with
  nobody named on it goes. `Foreword.Domain/Install/OwnerColumn` replaces all three — **proposed** from
  the signed-in account (the calendar screen already knows which addresses belong to whom), an explicit
  choice always winning, and falling back to what the app did before the setting existed so a phone
  that has been delivering for months does not change its mind on a version bump.
  `NobodyIsTheDefaultTests` is the guard; naming a person is *not* the offence, since the household
  roster, the per-column hues and the vision prompt all name all four and all of those are about the
  **columns**, which exist on both installs.
- **The shared vault holds household facts; the personal vault holds per-install ones.** This is the
  distinction Release I turns on, and the obvious place to put "whose phone is this" is wrong:
  `CalendarMappingOptions` rides `ForewordSecrets.CalendarMappingJson` inside the **shared**
  `storyworthtelling-secrets.json`, which both installs read and only one writes (`VaultOwnership`), so
  a per-install field there would be restored from the first phone onto the second and its owner's
  handwriting would start filing under somebody else — silently. So `InstallOptions` is its own bag,
  built fresh by the head and never deserialised from a shared document, backed up to

## Languages & Frameworks

- **Primary**: C# / .NET
- **Frontend** (when needed): Angular
- **Mobile** (when needed): .NET MAUI
- **IDE**: Visual Studio

## Project Structure

Each project lives in a single `.sln` with multiple `.csproj` files — typically split by concern (e.g. `Domain`, `Infrastructure`, `API`, `Tests`). Keep projects coarse-grained until complexity actually demands splitting.

## Architecture Preferences

- Object-oriented; avoid functional-style abstractions that don't fit naturally in C#.
- Controllers handle HTTP; services handle logic; EF Core `DbContext` is the data access layer. Do not add a repository layer on top of `DbContext`.
- Do not access `DbContext` directly from controllers or above the service layer.
- Prefer fewer layers over more. Avoid redundant typecasts and pass-through classes that add no value.
- Use SignalR for pushing real-time updates to clients.
- Expose APIs via controllers with Swagger documentation.

## Code Style

Follow standard Microsoft C# naming conventions throughout. Do not use underscores in any identifier — this includes private fields (use `camelCase`, not `_camelCase`).

## Async

Use `async`/`await` only where I/O actually warrants it or where it will meaningfully improve expected performance. Do not make everything async by default.

## Error Handling

Handle errors where they occur. Propagate failures with a descriptive, specific message and preserve the stack trace for debugging. Do not swallow exceptions or replace them with vague messages.

## Testing

- Unit tests for all logic; integration tests at the API boundary.
- TDD strictly: tests are written before implementation.
- Do not skip or defer tests — untested code is not considered done.

## Dependencies

Only add a dependency if one of these is true:
1. It is already present in the project.
2. It is from Microsoft or another well-established, trusted publisher.
3. It is required to integrate with the specific tool or service being built.

When in doubt, implement it directly in C#.

## Git Workflow

- **Never push to `main`**. All changes go on a feature branch for review first.
- Open a pull request and wait for approval before merging.

## Graphify

A local code-knowledge-graph CLI (`graphifyy` on PyPI, installed via `uv tool install graphifyy`; binary is `graphify`). Parses the repo with tree-sitter — no code leaves the machine; only doc/PDF/image extraction (unused so far here — see below) optionally calls an LLM. Installed project-scoped (`.claude/skills/graphify/SKILL.md`, `.claude/CLAUDE.md`), **not** the global `--strict` PreToolUse-blocking mode — the registered `PreToolUse` hooks in `.claude/settings.json` (`graphify hook-guard search|read`) only nudge, they don't block (confirmed: they exit 0 on Bash/Grep/Read/Glob regardless).

- **Query instead of grepping — but seed it with real identifiers, not a question.** `graphify query "<terms>"` does BFS from whichever graph nodes best match each *word* in the string, not semantic understanding of a sentence. `graphify query "How does a bad API key get detected and cause a settings field to reappear?"` matched on "Settings"/"Key"/"ApiKey" and returned 13 nodes of noise (NYT API options, an unrelated test method) — nothing about credential health. `graphify query "CredentialFieldState CredentialHealth AuthFailure ICredentialHealthSink"` (the actual type names) found the real chain in the same second, and surfaced something a manual grep pass missed on the first try: four apps (Foreword, Ledger, Storyboarder, FocusPhone) each have their own `CredentialHealthStore` implementing the same pattern. **So: skim `graphify god-nodes` or a quick grep for the relevant type/method names first, then feed those names to `query`.** `graphify path "<A>" "<B>"` (add `--undirected` if the directed search comes back empty) and `graphify explain "<concept>"` are similarly name-seeded, not question-seeded, and both stay at file/import granularity — they didn't surface the `MarkFailing()`-write → `CredentialFieldState.Decide()`-read data flow (it crosses a Preferences/Drive persistence boundary, not a direct call), only that both sides import the same namespace. `graphify god-nodes` for architectural hubs. All of this reads `graphify-out/graph.json` directly (~1s, no LLM). Fall back to `GRAPH_REPORT.md` or raw grep when even a symbol-seeded query comes back empty, or when tracing a flow that crosses a persistence/IPC boundary the graph doesn't model.
- **Nothing under `graphify-out/` is committed — rebuild it fresh each session.** `graphify update . --no-cluster && graphify cluster-only . --no-label --no-viz` (~25s cold on this repo's 1342 files, ~1-2s incremental within a session via the AST cache). Both steps are local CPU work only — `--code-only` extraction never touches the network and `--no-label` skips the one LLM-calling step that exists — so a rebuild costs wall-clock time, **not tokens or API spend**; there's no reason not to just redo it. `update` alone re-extracts (content-hash-keyed, so it's cheap even after a big pull) but does *not* re-run clustering, so community numbers/`GRAPH_REPORT.md` go stale until `cluster-only` runs too. `--no-label` skips LLM community naming (no backend key configured here — communities are `Community N` placeholders); drop it and set e.g. `GEMINI_API_KEY`/`ANTHROPIC_API_KEY` if named communities are ever wanted (that step *does* call an LLM and cost tokens/API spend, unlike everything else here).
- **Why it's gitignored, not committed:** first tried committing `graph.json`/`GRAPH_REPORT.md`/`manifest.json`/`.graphify_analysis.json` for instant fresh-clone access. Turned out community-ID assignment isn't stable across `cluster-only` runs — a 2-line CLAUDE.md edit produced a 35%-churned, ~30MB diff (298,074 of 846,056 lines) with no real code change behind it. Two commits alone added ~61MB of permanent blob history for a few lines of real change. Since the rebuild is free of token/API cost, that trade isn't worth it — `graphify-out/` (the whole directory: cache, graph.json, GRAPH_REPORT.md, manifest.json, .graphify_analysis.json, cost.json if an LLM-backed step ever runs) is gitignored, and every session just rebuilds on first use.
- **Repo-specific findings from building it here:** `--code-only` extraction of the full repo (1342 files: 1267 `.cs` + `.csproj`/`.xaml`/`.sln`/shell scripts) via `tree-sitter-c-sharp` took ~12s and produced 16k+ nodes / 40k+ edges with only **one** parse failure — `Storyworthtelling.Maui.Tests/PaperKitTests.cs:157`, an interpolated verbatim string (`$@"...{family}..."` with embedded `""`) the C# grammar partially mis-parses; the file still contributed 26 extracted symbols, so it's a minor gap, not a blocker. `.yml` workflow files and `.xml`/font/image assets aren't extracted (not classified as code or docs); `god-nodes` output lines up with the real hubs this file already documents (`Codex.Domain.Music`, `Track`, `Novel`, `ForewordTask`, `FolioDbContext`, …), which is a decent sanity check that the graph is trustworthy. Doc/PDF/image extraction (the 44 `.md` files, `.png`/`.jpg` assets) was **not** run — that path needs an LLM call per file and no backend key is set up in this environment; run `graphify extract .` (i.e. drop `--code-only`) to add it later if doc-aware queries become worth the API cost.
