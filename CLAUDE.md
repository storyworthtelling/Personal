# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal projects repository — primarily background automation apps, with occasional MAUI mobile apps and Angular frontends. Projects are added incremenledger; update this file with project-specific build/test commands when a new one lands.

## Design

**`DESIGN.md` at the repo root is the Paper & Ink design bible** — the single source of truth for palette, typography, motion, materiality, spacing, components, PDF page specs, icon specs, voice, and accessibility across every project. Rules that matter when writing code:

- **No color hex or type-size literals outside the registered token files** (DESIGN.md §16). Leak-guard unit tests in every project enforce this; consume tokens instead (`FocusPhone.Domain.Design.DesignTokens` + `FocusPhone.Ui.Android` `PaperUi`/`PaperTheme` for FocusPhone, `Storyboarder.Domain.Design.DesignTokens` + `Resources/Styles/DesignTokens.xaml` styles for the MAUI apps).
- The six shared fonts live in `/Fonts` (Source Serif 4, Source Sans 3, Cascadia Code — static TTFs, OFL). Native heads package them as assets via `FocusPhone.Ui.Android`; MAUI heads via `<MauiFont>`; the Skia renderers via embedded resources (`EmbeddedTypefaces`).
- **Interaction rules are load-bearing** (DESIGN.md §5–§11): success is an inline state change (no success toasts/alerts), destructive acts are undo-first (an `UndoBar` window, not a confirm dialog), loading is a status sentence not a spinner, primary actions live in a pinned bottom bar, screens open with a Serif in-page header, time is 12-hour and list timestamps are relative (`RelativeTime`/`TimeFormats`, duplicated per Domain and kept identical by a parity test).
- **Generated artifacts** (icons, the paper-grain tile, the owner branding medallion) are all produced by the committed **`Tools/IconStudio`** console: `dotnet run --project Tools/IconStudio -- --repo-root .` (tests: `dotnet test Tools/IconStudio.sln`). Never hand-edit generated resources. **Owner photo swap:** drop a square image at `/Branding/owner.png` and rerun IconStudio — it circle-masks the photo into the medallion for every consumer (PDF covers + settings screens) and never clobbers an existing `owner.png`.
- **Owner's voice is pending** (DESIGN.md §11): the intent is to learn the owner's wit from their self-authored Google Drive docs, which needs the Google Drive connector authorized in claude.ai. Until then copy stays quiet-neutral.
- New projects start on-system: see DESIGN.md §15 for the MAUI/Angular defaults.

- **Podcast fetch speed (cold-start cache + parallel refresh):** episodes were never persisted — every launch rebuilt them in-memory and opened on a blank "Fetching episodes…" while feeds fetched **sequentially** (N shows = N serial round-trips). Now the last fetch is cached on-device (`EpisodeCacheStore` prefs → `PodcastCache` domain record + unit-tested `PodcastCacheCodec`) and `LoadCachedEpisodes` paints the shelf instantly on launch; `RefreshFeedsAsync` then refreshes **all feeds concurrently** (`Task.WhenAll` over `FetchFeedAsync`, wall time = the slowest feed) in the background and updates the shelf in place. The refresh is **cache-preserving**: it starts from the cached episodes pruned to still-subscribed feeds and only replaces feeds that fetched successfully, so a flaky network keeps a show's last-known episodes instead of dropping it; per-feed failures are summarized in one toast rather than a wall of them. The cache is purely local (episodes are re-derivable from feeds — deliberately excluded from the Drive backup above).
- **Music scan (incremental + bounded-parallel):** the Music side already loads its catalog from a local SQLite cache (`MusicCatalogCache`) on launch, so browse is instant/offline; the slow part was the scan, which cleared the cache and re-read every file's tags **sequentially** over Drive. Now `MusicScanner` is **incremental**: it diffs the Drive listing against the cache's stored per-file change signature (modified-time + size — new `modifiedTimeTicks`/`sizeBytes` columns, added to old caches by an in-place `ALTER TABLE` migration) via the pure, unit-tested `MusicScanPlan.Compute`, then only re-reads new/changed files and deletes tracks whose file is gone (no more clear-and-rebuild). The tag reads run in **bounded-parallel batches** (`MaxConcurrentReads = 8`, `Task.Run` + `Task.WhenAll`) — bounded to respect the Drive quota/mobile radio and because `MusicCatalogCache` is a single `SqliteConnection` (not safe for concurrent writes), so each batch of parallel reads lands in **one serialized transaction** (the versioned `Upsert` overload). Progress is reported over the files actually being read, so a rescan that changed little finishes fast. `MusicScanPlan` + the cache versioning are unit-tested; the scanner's Android wiring is compile-checked in CI.

### Storyboarder

An **Android (MAUI) app** that turns a Google Docs novel into a multi-volume graphic novel: Claude builds a design bible and storyboards the book; Gemini renders the panels; a resumable pipeline assembles one PDF per volume. After the volumes, a final `ComposingAnalysis` stage produces one additional **book-analysis (revision) PDF** per novel — Claude map-reduces the manuscript into a report (character map + arcs, plot holes, inconsistencies/inaccuracies, multi-perspective reviews, a prioritized revision plan, plus line-level edits, prose style & voice, dialogue critique, a scene-by-scene breakdown, and an **authorial-voice-consistency** read that flags where the manuscript's own prose drifts from its dominant voice) that is rendered to raster pages via SkiaSharp and wrapped by the existing image-based PDF composer (no PDF-text/font machinery). Chapters are detected at ingestion (`ChapterDetector`) so every finding cites a chapter; the reduce is a **story half** and a **craft half** (two Claude calls, persisted separately, because one reply can't carry both without truncating or outlasting the background worker), plus separate resumable calls for the web-searched **fact checks** and the **voice-consistency** read (`AssessVoiceConsistency`, which needs per-chapter prose samples, not the notes) — each stored in its own column and folded into the report at render. `Novel.ReportOnly` skips every art stage and runs the design bible straight into the report. Modeled on DailyLoader: an AndroidX **WorkManager** periodic worker drains the pipeline on-device (no web host, no SignalR). See `Storyboarder/`.

- Tests: `dotnet test Storyboarder/Storyboarder.sln -p:StoryboarderTfms=net10.0` (Domain + Infrastructure + Tests; no device, no API keys — external services are faked). The `-p:StoryboarderTfms=net10.0` switch builds Infrastructure for the desktop TFM only so the suite runs without the MAUI/Android workload.
- Android head (`Storyboarder.Android`, `net10.0-android`, app id `com.storyworthtelling.storyboarder`): build with the MAUI/Android workload + Android SDK (same minimal-SDK note as FocusPhone — `platforms/android-34/`, `-p:AndroidSdkDirectory=<sdk> -p:AndroidUseApkSigner=false`); signs with the default debug keystore. Background work uses `Xamarin.AndroidX.Work.Runtime`.
- Secrets are entered in-app on the Settings page (stored in MAUI `Preferences`): Claude + Gemini API keys. Google Docs access uses native device-account sign-in via Android `AccountManager` (no Play Services binding, so **no `dl.google.com` build dependency** — unlike the FocusPhone Camera app); a Drive doc picker lists the user's Google Docs. Sign-in requires the app to be registered as an **Android OAuth client** (package `com.storyworthtelling.storyboarder` + signing-cert SHA-1) in a Google Cloud project with the Docs+Drive APIs enabled and the user added as a test user, else it fails with `UnregisteredOnApiConsole`; the Settings page surfaces the exact package + SHA-1 to register (see `Storyboarder/README.md`).
- The launcher icon is **native** Android adaptive-icon resources under `Storyboarder.Android/Resources/mipmap-*` (`mipmap-anydpi-v26/appicon.xml` + per-density `appicon`/`appicon_foreground` PNGs + `values/colors.xml`). MAUI's `MauiIcon`/resizetizer pipeline is **bypassed**. Two load-bearing details make it actually ship (both apps had the *default* icon until fixed — DailyLoader too, with `ic_launcher` naming): (1) the resources live in the plain **`Resources/`** folder, **not** `Platforms/Android/Resources`. These heads don't set `<SingleProject>true</SingleProject>`, so MAUI never repoints the Android resource prefix — it stays the .NET-for-Android default `Resources`, and the active glob is only `Resources/*/*` (one level, specific extensions; that's also why `Resources/Styles/DesignTokens.xaml` is left alone). Anything under `Platforms/Android/Resources` is silently dropped. (2) `android:icon` is set via `[Application(Icon="@mipmap/appicon", RoundIcon="@mipmap/appicon_round")]` on `MainApplication` — **not** the XML `AndroidManifest.xml`, which (same reason) isn't wired into these heads at all (that's why permissions live in `[assembly: UsesPermission]` attributes too). The CI `build` job runs an **ICON CHECK** (`aapt2 dump badging` + `unzip`) that reads the resolved `android:icon` back out of the APK and **fails the build if it's empty** — a green build now proves the custom icon is present. (Launchers cache icons across same-signature updates — uninstall/reinstall or reboot to see a new icon.) All icon resources are (re)generated by the committed `Tools/IconStudio` console — see the Design section above.
- `Storyboarder.Infrastructure` multi-targets `net10.0;net10.0-android`; `Storyboarder.Domain` is `net10.0`. Data layer is EF Core + SQLite (the prescribed data-access choice); SkiaSharp composes pages, PdfSharp assembles volume PDFs. On device the DB and image/PDF output live under `FileSystem.AppDataDirectory` (volume PDFs at `<novelId>/volumes/volume-N.pdf`, the analysis report at `<novelId>/analysis/book-analysis.pdf`).
- **Volume binding (performance + covers):** after storyboarding, pages are decomposed **one volume per chapter** (`VolumeDecomposer`, capped by `PageLayoutOptions.MaxPagesPerVolume`; a chapter over the cap splits into parts at scene boundaries), replacing the model's own split — a 338-page single volume once wedged assembly for days. Binding still appends one page per worker cycle, and `FileSystemImageStore.Save` writes **atomically** (temp file + rename) so a worker force-stop mid-write can't leave a truncated PDF (the `PdfReader` "StartXRef" retry loop). Each volume gets a **spoiler-free comic cover**: Claude writes a cover concept from the chapter (`IClaudeAnalysisClient.DescribeVolumeCover`), Gemini renders it in the book's art style, and `CoverPageRenderer.VolumeCover` typesets the novel + chapter name over it (cover art at `<novelId>/volumes/volume-N-cover.png`); any failure degrades to the plain typographic cover, never blocking binding. Entity extraction (`ExtractEntities`) runs on the **strong** Claude model — the cheap tier under-extracted minor characters and described sets, starving reference-sheet coverage (one book fell from ~216 sheets to ~55) and causing wrong/duplicate characters and location drift in renders; per-chunk analysis notes stay on the cheap tier.
- EF migrations run against the desktop TFM: `StoryboarderTfms=net10.0 dotnet ef migrations add <Name> --project Storyboarder/Storyboarder.Infrastructure --framework net10.0` (a `DesignTimeDbContextFactory` supplies the context; the env var keeps the Android TFM out of the design-time build). In practice the migrations here are **hand-written** (no `dotnet ef` run in the sandbox): each needs the `.cs`, a `.Designer.cs` mirroring the current `StoryboarderDbContextModelSnapshot`, and a snapshot update — snapshot drift fails `MigrationSafetyTests` at runtime, not at compile time.
- **Drafts (Phase 2):** a `Novel` is one *draft*; a *project* is the book being revised, grouping drafts by `ProjectId` (first draft's ProjectId = its own Id). Each `Panel` records the source-text span `[SourceStartOffset, SourceEndOffset)` of the storyboard window it came from (window granularity — all panels of a window share its span). `ProjectService.CreateNextDraftAsync` adds a draft from a re-picked doc; `GetDraftDiffAsync` diffs a draft against its `PreviousDraftId` (findings resolved/new + changed panels); and storyboarding reuses a prior draft's panels+renders for any window whose text is byte-identical, so a revision re-illustrates only what moved. `PanelSourceMatching` is the single definition of "same source span" shared by the diff and the reuse. The Android UI invokes both from a project card ("New draft (re-pick doc)" and "What changed since last draft"), and an in-app reader (`ReaderPage` with chapter jump + `PageZoomPage` pinch-zoom, `ReportPage`, and a before/after `DraftDiffPage`) reads finished books without opening the PDF. `scripts/setup-android-build.sh` makes the head compile in a web/CI container (the official `android.jar` host is network-blocked, so it pulls API 36 from a GitHub mirror and stitches a minimal SDK at `/opt/android-sdk-min`); build with `-p:AndroidSdkDirectory=/opt/android-sdk-min -p:AndroidUseApkSigner=false` (it does not run the app — no emulator/display).
- **Art & layout (Phase 4):** each `Panel` carries a `ShotType` (Standard/Wide/Splash) the storyboard model tags; `PageLayoutCalculator`'s shot-aware `Layout` keeps an all-Standard page identical to the old uniform grid while a Wide shot becomes a full-width band and a Splash gets its own page (`SplitForPages`). `DialogueFit` abridges dialogue to a balloon budget, and `IClaudeAnalysisClient.DeriveArtStyle` derives one book-wide style from the prose+cast at design-bible time unless the user picked one. **Lettering:** the composer draws a tail on spoken balloons and a bubble trail on thought balloons (`Panel.DialogueKind`), and letters a sound effect over the art as display type (`Panel.Sfx`); the storyboard model tags both. **Storyboarding is deliberately minimalist** — the prompt asks for the fewest load-bearing panels (a distinct action, who, where), skipping transitional/in-between beats, since the graphic novel is a comprehension aid (also cheaper/faster to render). Deferred (owner-flagged, not automated): off-model auto-detection. The lettering *look* is compile-verified only — it needs eyes on a device.
- **Sources & data safety (Phase 5, partial):** sources are Google Docs **and `.docx`** — `DocxTextExtractor` (pure, in `Storyboarder.Domain/Text`) reads a .docx's `word/document.xml`, and `GoogleDocsClient` detects a picked file's Drive mime type to route (Docs API vs Drive byte-download + extract), so nothing above it changed (`Google.Apis.Drive.v3` is now an Infrastructure dep). `ProjectService.VerifyAndHealOutputsAsync` runs at app start (`MainActivity`) to heal any "done" unit whose file went missing after a reboot, regressing the novel so the pipeline rebuilds it. Owner's-voice propagation is still pending the owner's Drive docs.
- **Gemini throughput (Phase 6):** `RateLimitOptions.GeminiRequestsPerDay` is a safety ceiling (60/min, 5,000/day) sized under the owner's real tier (2,000/min, 50,000/day), not at it. A **batch renderer** runs by default (`GeminiOptions.UseBatchRendering = true`): `IGeminiBatchClient`/`GeminiBatchImageClient`, in-flight state (`Panel.BatchAttempted`, `Panel.BatchJobId`/`Panel.BatchSubmittedAtUtc`, `WorkStatus.SubmittedToBatch`), and `GraphicNovelProcessor.RunBatchStep`. Batching is **per-scene, not per-book**: Claude tags scene boundaries at storyboard time (`Panel.NewScene`), and `RunBatchStep` submits **one job per scene** (a scene past `GeminiOptions.BatchMaxPanelsPerJob` is split across jobs), running up to `MaxConcurrentBatchJobs` scene jobs at once — so a book runs several small jobs instead of one giant one (the owner's first run wedged a single 664-panel job for days). Each cycle polls/reconciles every in-flight job, **gives up on any job older than `BatchGiveUpHours`** (its panels fall back to synchronous rather than freeze the book forever), recovers panels stranded with no job id, and logs result-to-panel **correlation gaps** (stray keys / unmatched panels) so a mis-correlation is diagnosable. Any panel a batch fails or blocks falls back to the synchronous render + `HandleBlockedPanel` ladder (first attempt batched, escalations synchronous). Reference sheets go through the **Files API** (`SubmitAsync` uploads each distinct sheet once, deduped by content hash, and references it by `fileData` URI) so a full book stays under the ~20 MB inline batch ceiling. The Batch REST envelope + the Files API upload protocol are reconstructed from Google's docs and **not yet live-verified** — the first real run is the verification, and every mismatch path degrades to synchronous rendering (safe, not crashy); see `BATCHING.md`. Set `UseBatchRendering = false` to force the fully-synchronous path. (`Novel.BatchJobId`/`BatchSubmittedAtUtc` are legacy single-job columns, retained but unused.)
- **Owner's voice (cross-cutting):** a shared **`Storyworthtelling.Voice`** library (net10.0, pure .NET, at the repo root — its own `.csproj` + `.Tests`) learns the owner's writing voice from the documents they upload and writes situational app messages in it; every com.storyworthtelling app references it (a `<ProjectReference>`, so the DLL ships in each APK — Storyboarder.Infrastructure references it today). Pieces: `VoiceProfile` (stored as JSON in Drive), `IVoiceClient`/`VoiceClient` (Claude, raw non-streaming HTTP — `RefineAsync` distils a profile from a document, `ComposeAsync` writes one message; reads its key live via `IOptions<VoiceOptions>`, default models `claude-sonnet-4-6` / `claude-haiku-4-5-20251001`), `IVoiceProfileStore`/`DriveVoiceProfileStore` over a narrow `IDriveTextFile` seam (`DriveTextFile` is the Google glue), and **`VoicedMessenger`** — the entry point apps call: it loads the profile, composes fresh, and **degrades to the neutral fallback (never throws)** when there's no profile/key or a call fails, so static labels stay minimalist and only situational messaging is voiced. In Storyboarder the pipeline refines the voice from each manuscript at **ingestion** (best-effort, guarded by `Novel.VoiceAnalyzed` so it runs once per draft), and `MainPage` shows a voiced welcome that stays hidden until a profile exists. Tests: `dotnet test Storyworthtelling.Voice.Tests/Storyworthtelling.Voice.Tests.csproj` (fake HTTP + in-memory store; no key). **The Claude key lives in ONE Drive config file** (`VoiceConfig`/`DriveVoiceConfigStore`), published by Storyboarder's settings and read by every other app via `DriveVoiceOptions` (an `IOptions<VoiceOptions>` that pulls the key from Drive on `RefreshAsync`) — so there are no per-app key screens. The profile + config are ONE Drive file each, found by name: Storyboarder writes them under the full `drive` scope; the reader apps use **read-only** `drive.readonly`. **Rolled out to every app:** Ledger greets on its balances screen; DailyLoader greets on its delivery screen (reusing its existing Google device account, with `drive.readonly` added to its token scope); the FocusPhone Launcher, Audio, and Communication heads greet via a shared `FocusPhone.Ui.Voice.VoiceGreeting` (+ `VoiceGoogleAccount` sign-in for heads without their own Google account — Audio reuses its music account). The library **multi-targets `net9.0;net10.0`** (its Extensions deps pinned to 9.0.0) because DailyLoader's head is on net9.0-android while the rest are net10.0-android — each consumer picks the matching asset. Each reader app adds device-account Google sign-in and degrades to neutral/hidden copy when the profile, key, or Drive access isn't there. The owner registers each app as an OAuth client (the noted scope) and enters the Claude key once in Storyboarder. **Not yet done:** live-API verification of `VoiceClient` and the Drive reads on a real device.

### Secrets vault (cross-cutting)

Every app's keys and durable "magic strings" live in **ONE AES-256-GCM-encrypted file in the owner's Google Drive** (`storyworthtelling-secrets.json`), so the FocusPhone cutover's factory reset — which wipes every on-device store — no longer means re-entering every credential by hand. The vault types live in the shared **`Storyworthtelling.Voice`** library under the `Secrets/` folder (`Storyworthtelling.Voice.Secrets`), reusing its existing `IDriveTextFile`/`DriveTextFile` Drive seam: `SecretsVault` (a record with one section per app), `SecretsCrypto` (PBKDF2-SHA256 → AES-GCM, **BCL only**, no new dependency; a wrong passphrase fails the GCM tag as `WrongPassphraseException`), `SecretsEnvelope` (the on-Drive `{version,kdf,iterations,salt,nonce,ciphertext,tag}` shape), `ISecretsVaultStore`/`DriveSecretsVaultStore` (load returns a `SecretsVaultLoadResult` distinguishing Empty/Loaded/WrongPassphrase/Corrupt), and `SecretsVaultService` (the per-app orchestration: `LoadAsync` for restore, `PublishAsync(merge)` for a per-section save that never overwrites a vault it couldn't read). Fully unit-tested in `Storyworthtelling.Voice.Tests/Secrets/`. **Two-way, encrypted:** each app publishes its section on settings-save (and on connect/pair events — Ledger on a Plaid link, DailyLoader on a reMarkable register, Communication on Gmail save) and restores missing values on startup; the owner enters one **passphrase per app** (the single thing NOT in the vault — wiped by the reset, re-entered once, then unlocks the rest). The vault is the **single source of truth for the shared Claude key**, replacing the old plaintext `storyworthtelling-voice-config.json`: `VaultVoiceConfigStore` adapts the vault to the existing `IVoiceConfigStore` seam, so the voice stack is unchanged — MAUI apps swap the DI registration; the FocusPhone `VoiceGreeting`/`MusicTasteService` build it directly. Per-app wiring: MAUI apps add a `VaultPassphrase` to their settings store + a `VaultSync` helper + a restore hook in `MainActivity`; the FocusPhone native heads share `FocusPhone.Ui.Voice.VaultPassphraseStore` + `SecretsVaultAccess` and restore in each head's launch Activity. **Ledger's per-bank Plaid access tokens** (generated on-device, in SQLite) are backed up via `AccountService.GetInstitutionCredentialsAsync`/`RestoreInstitutionsAsync` (unit-tested), so a reset restores every bank without re-linking. **Scope change:** writing the vault needs full `drive`, so Ledger + DailyLoader widen their token scope from `drive.readonly` to `drive` and FocusPhone's `VoiceGoogleAccount` does the same (the owner re-registers the scope; until then publish/restore degrade quietly and apps keep working from local settings). **Not yet done:** live-API verification on a real device (same as the Voice rollout).

**Vault passphrase field:** the one secret NOT in the vault, so every settings screen shows it **in the clear** (not a masked password field) — it must be read back and set identically in each app, and Android blocks clipboard copy on password-typed fields. (The Gmail app password and Plaid secret stay masked — those aren't the vault key.)

**Credential health → settings declutter (cross-cutting):** because the vault backs up and restores every key, a working key is a done state, not something to keep on screen. Shared, unit-tested types in **`Storyworthtelling.Voice`** under `Health/` (`Storyworthtelling.Voice.Health`): `CredentialHealth`/`CredentialHealthReport` (+ `CredentialHealthCodec` JSON), `AuthFailure.IsHttpCredentialRejection` (401/403, plus Gemini's HTTP-400 `API_KEY_INVALID`), `ICredentialHealthSink` (write seam), and `CredentialFieldState.Decide(isSet, health)` — the pure rule that a key field is shown **only** when it's missing or a live call with it was just rejected; a working key collapses to a "Working ✓" line with a **Replace** button. Each app's API clients report health at their HTTP choke point through an **optional** `ICredentialHealthSink` ctor param (default null, so existing client unit tests are untouched; DI injects it because `AddHttpClient` uses `ActivatorUtilities`), and a Preferences/SharedPreferences-backed `CredentialHealthStore` per head persists the report and is read by the settings screen. Only auth rejections flag a key — throttling/5xx/network are left alone so a blip never falsely reveals a field. Per-app credential ids + classifiers: Storyboarder (`claude`/`gemini`), Ledger (`plaid`, via `PlaidFailure` over Plaid `error_code` — item/token errors are a per-institution concern, not the shared credentials), DailyLoader (`nyt-api-key`/`nyt-cookie`/`remarkable`/`anthropic`), FocusPhone Communication (`gmail-app-password`, via MailKit `AuthenticationException` in `CommunicationSync`) and Launcher (`github-update-token`, via `GitHubReleaseClient`'s status-carrying exception in `UpdateService`). Ledger/DailyLoader `Infrastructure` gained a `Storyworthtelling.Voice` reference for the seam (DailyLoader bumped `Google.Apis.Auth` to 1.75.0 to match). Pure logic is unit-tested; the settings-screen wiring in the Android heads is compile-checked in CI, live-verify pending like the rest of the Voice/vault rollout.

### Ledger

An **Android (MAUI) app** that shows balances across your banks, credit cards, and loans in one place by connecting to the **Plaid** aggregator (no US consumer bank offers a per-user balance API directly). Modeled on Storyboarder/DailyLoader: an AndroidX **WorkManager** periodic worker refreshes each connected institution on-device (no web host, no backend), EF Core + SQLite stores the latest balances/liabilities, and a Paper & Ink list displays them. See `Ledger/`.

- Tests: `dotnet test Ledger/Ledger.Tests/Ledger.Tests.csproj -p:LedgerTfms=net10.0` (Domain + Infrastructure + Tests; no device, no keys — Plaid is faked via `FakeHttpMessageHandler`/Moq). The `-p:LedgerTfms=net10.0` switch builds Infrastructure for the desktop TFM only so the suite runs without the MAUI/Android workload.
- Android head (`Ledger.Android`, `net10.0-android`, app id `com.storyworthtelling.ledger`): build with the MAUI/Android workload + Android SDK (same minimal-SDK note as Storyboarder); signs with the shared repo keystore secrets. Background work uses `Xamarin.AndroidX.Work.Runtime` (daily `PeriodicWorkRequest` + a one-shot for "Refresh now").
- **Secrets & data model:** the Plaid **client id/secret + environment** are entered on the Settings page (stored in MAUI `Preferences`, read live by the worker via `LiveOptions<PlaidOptions>`); per-institution **access tokens** live in the SQLite DB (`Ledger.Domain.Model.Institution`). The DB is at `FileSystem.AppDataDirectory/ledger.db`. There is no backend by design — for a personal single-user app the credentials-in-Preferences tradeoff is accepted (see `Ledger/README.md`).
- **Connecting an account (net-new vs the other apps):** a "Connect an account" button opens **Plaid Hosted Link** in a `WebView` (`PlaidLinkPage`); the app creates the `link_token` and, on Done, reads the completed session's `public_token` via `/link/token/get`, exchanges it for an `access_token`, and records the `Institution`. This connect seam is the one piece to finalize against Plaid's current Hosted Link docs (redirect/session handling); everything after it (refresh → SQLite → display) is fully covered.
- **Data pulled:** `/accounts/balance/get` for every account, plus `/liabilities/get` (next payment due/amount + APR) for credit cards and mortgages. Auto/home-improvement loans and some credit unions may be unsupported by Plaid → fall back to manual awareness. The account list also shows the credit limit where Plaid reports one, and each account row **expands to recent transactions** loaded on demand from `/transactions/get` (last 30 days) — this is a UI-side fetch, not part of the background refresh, so no extra tables. Transactions is a Plaid **subscription product** (billed per Item in production; the link token requests it as the required `product` — Plaid rejects a link token with an empty products array — while `liabilities` goes in `required_if_supported_products` so deposit-only institutions still link).
- The launcher icon is **native** Android adaptive-icon resources under `Ledger.Android/Resources/mipmap-*`, generated by `Tools/IconStudio` (glyph `Glyphs.Ledger` — the four-plus-one ledger marks). Unlike the other apps, Ledger's generated icon binaries are **not committed**; the CI `build` job regenerates them with `dotnet run --project Tools/IconStudio` before building, and the same fatal **ICON CHECK** (`aapt2 dump badging`) proves the custom icon is in the APK. Design tokens are registered in DESIGN.md §16 with the usual leak-guard + parity tests.
- `Ledger.Infrastructure` multi-targets `net10.0;net10.0-android`; `Ledger.Domain` is `net10.0`. EF migrations run against the desktop TFM: `LedgerTfms=net10.0 dotnet ef migrations add <Name> --project Ledger/Ledger.Infrastructure --framework net10.0` (a `DesignTimeDbContextFactory` supplies the context). APK builds in CI via `.github/workflows/build-ledger.yml`.

## Project Structure

Each project lives in a single `.sln` with multiple `.csproj` files — typically split by concern (e.g. `Domain`, `Infrastructure`, `API`, `Tests`). Keep projects coarse-grained until complexity actually demands splitting.

## Architecture Preferences

- Object-oriented; avoid functional-style abstractions that don't fit naturally in C#.
- Controllers handle HTTP; services handle logic; EF Core `DbContext` is the data access layer. Do not add a repository layer on top of `DbContext`.
- Do not access `DbContext` directly from controllers or above the service layer.
- Prefer fewer layers over more. Avoid redundant typecasts and pass-through classes that add no value.
- Use SignalR for pushing real-time updates to clients.
- Expose APIs via controllers with Swagger documentation.

## Code Style

Follow standard Microsoft C# naming conventions throughout. Do not use underscores in any identifier — this includes private fields (use `camelCase`, not `_camelCase`).

## Async

Use `async`/`await` only where I/O actually warrants it or where it will meaningfully improve expected performance. Do not make everything async by default.

## Error Handling

Handle errors where they occur. Propagate failures with a descriptive, specific message and preserve the stack trace for debugging. Do not swallow exceptions or replace them with vague messages.

## Testing

- Unit tests for all logic; integration tests at the API boundary.
- TDD strictly: tests are written before implementation.
- Do not skip or defer tests — untested code is not considered done.

## Dependencies

Only add a dependency if one of these is true:
1. It is already present in the project.
2. It is from Microsoft or another well-established, trusted publisher.
3. It is required to integrate with the specific tool or service being built.

When in doubt, implement it directly in C#.

## Git Workflow

- **Never push to `main`**. All changes go on a feature branch for review first.
- Open a pull request and wait for approval before merging.
