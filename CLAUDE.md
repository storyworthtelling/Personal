# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal projects repository — primarily background automation apps, with occasional MAUI mobile apps and Angular frontends. Projects are added incremenledger; update this file with project-specific build/test commands when a new one lands.

## Design

**`DESIGN.md` at the repo root is the Paper & Ink design bible** — the single source of truth for palette, typography, motion, materiality, spacing, components, PDF page specs, icon specs, voice, and accessibility across every project. Rules that matter when writing code:

- **No color hex or type-size literals outside the registered token files** (DESIGN.md §16). Leak-guard unit tests in every project enforce this; consume tokens instead (`Codex.Domain.Design.DesignTokens` + `Codex.Ui.Android` `PaperUi`/`PaperTheme` for FocusPhone, and the shared **`Storyworthtelling.Maui`** kit for the MAUI apps — Foreword and Folio have adopted it and so have no palette of their own; **Ledger** is the last head still carrying `Ledger.Domain.Design.DesignTokens` + its own `Resources/Styles/DesignTokens.xaml`, and adopts the kit at its own phase).
- The **eight** shared fonts live in `/Fonts` (Source Serif 4 — Regular, Semibold, Italic and **Black** — Source Sans 3 Regular and Semibold, Cascadia Code, and **Pinyon Script**, the calligraphy hand DESIGN.md §4 reserves for the owner's voice; static TTFs, OFL). Note that the FONT CHECK in `build-flyleaf.yml` and `build-post.yml` names only six of them, omitting Serif Black (every screen header) and Pinyon Script (the voice); `build-plate.yml` checks all eight. Native heads package them as assets via `Codex.Ui.Android`; MAUI heads via `<MauiFont>`; the Skia renderers via embedded resources (`EmbeddedTypefaces`).
- **Interaction rules are load-bearing** (DESIGN.md §5–§11): success is an inline state change (no success toasts/alerts), destructive acts are undo-first (an `UndoBar` window, not a confirm dialog), loading is a status sentence not a spinner, primary actions live in a pinned bottom bar, screens open with a Serif in-page header, time is 12-hour and list timestamps are relative (`RelativeTime`/`TimeFormats`, duplicated per Domain and kept identical by a parity test).
- **Generated artifacts** (icons, the paper-grain tile, the owner branding medallion) are all produced by the committed **`Tools/IconStudio`** console: `dotnet run --project Tools/IconStudio -- --repo-root .` (tests: `dotnet test Tools/IconStudio.sln`). Never hand-edit generated resources. **Owner photo swap:** drop a square image at `/Branding/owner.png` and rerun IconStudio — it circle-masks the photo into the medallion for every consumer (PDF covers + settings screens) and never clobbers an existing `owner.png`.
- **Owner's voice is pending** (DESIGN.md §11): the intent is to learn the owner's wit from their self-authored Google Drive docs, which needs the Google Drive connector authorized in claude.ai. Until then copy stays quiet-neutral.
- New projects start on-system: see DESIGN.md §15 for the MAUI/Angular defaults.

  - **`ROLE_SMS`, and why it is load-bearing:** Post cannot send a text or delete one for real without it, because only the default SMS app may write to the provider. Android will not even *offer* the role unless four components are declared (`SMS_DELIVER` + `WAP_PUSH_DELIVER` receivers, a `RESPOND_VIA_MESSAGE` service, a `SENDTO` activity) — an app missing one is silently absent from the "default SMS app" list, so `FrozenInvariantsTests` asserts all four **with their intent filters**. Holding the role also makes Post **responsible for the record**: Android stops persisting incoming texts once a third-party app is default, and does not write sent ones either, so `SmsProviderWriter`/`SmsSender` do both — skip it and the phone's own copy of the owner's texts silently stops. The role is re-read on **every launch** (`SmsRoleAccess.CheckOnLaunch`) because a policy pass or an OS update can take it away, and the pure `SmsRole.Decide` distinguishes "never had it" from "just lost it" — the same missing role, two different sentences. **Risk #1 for the on-device plan:** the consent dialog may be suppressed by the lockdown (there is no device-owner API for this — no `SetDefaultSmsApplication` in the bindings), in which case Flyleaf's admin mode temporarily relaxes policy.
  - **A shared `Dictionary` was the actual cause of "Post stopped receiving texts."** The Mailbox's bulk file/delete work (`c587f8c`) put one `DeleteBuffer` behind both the UI thread (`Schedule`/`Undo`, from a tap and the undo timer's `Handler.PostDelayed`) and a background `Task.Run` (`Filter`, from `ReloadThreads`/`LoadMore`'s reload-and-merge path) — an access pattern a plain `Dictionary<TKey,TValue>` does not support. A concurrent read during a resize can corrupt its buckets and throw from inside the bare `Task.Run`, unhandled; on the app holding the SMS role, enough of those crashes gets Post force-stopped by Android, which silently stops delivering `SMS_DELIVER` to a stopped app's manifest receiver until the owner relaunches it by hand — which reads exactly like "texts stopped arriving" and, separately, like a role-request tap that "does nothing" if the crash lands mid-interaction. `DeleteBuffer` now locks every access; `DeleteBufferTests.ConcurrentScheduleUndoAndFilter_NeverThrowsOrCorrupts` runs a few thousand interleaved Schedule/Undo/Filter/TakeDue calls from two threads as a standing regression guard, though it — like any concurrency test — cannot guarantee reproducing every interleaving on every run.
  - **The MMS gap: Post now actually downloads what a WAP push announces.** A WAP push is a doorbell, not the message — it carries only a transaction id and a URL to fetch the real MMS from. `MmsDeliverReceiver` used to just log that one arrived; it now hands the raw PDU to `Codex.Domain.Post.MmsNotificationParser` (pure, unit-tested against synthetic OMA-WAP-209-encoded PDUs — field-name octets and value shapes came from AOSP's own `PduHeaders`/`PduParser`, not memory, and an unrecognised field stops the walk rather than risk misreading past it), then `MmsDownloader` reserves a provider row and calls `SmsManager.DownloadMultimediaMessage`. `MmsDownloadReceiver` gets the platform's completion callback and raises the same notification an incoming text does, reusing `SmsLogReader`'s existing (now `internal`) MMS address/text reads rather than a second copy of that query. **Not yet verified on-device** — nothing here has met a real MMSC — the parser is the part with a synthetic-PDU test suite behind it; the download-request and completion-callback shapes follow the platform's documented default-SMS-app contract but haven't been proven against a live carrier.
  - **The first MMS round-trip surfaced two more gaps behind the download itself: pictures/video landed as a bare "[MMS]" with nothing to open, and a group text fragmented into one thread per sender.** Both traced to `SmsLogReader`/`SmsRecordMapper` never having read past the single "from" address and the `text/plain` part. Fixed together, reusing domain support (`TimelineItem.GroupId`/`Participants`/`Attachments`, `TimelineMerger`'s group-vs-person threading, `MailboxArea`'s group title/action-row handling) that already existed — built for the gmbridge path, never wired to MMS: `SmsLogReader.ReadMmsAllAddresses` reads every `from`/`to`/`cc`/`bcc` row rather than the first match, and `SmsRecordMapper.MapMms` calls it a group (more than the sender-plus-you) once there are more than two distinct addresses, threading it on the system MMS/SMS provider's own `thread_id` (reused as `GroupId` rather than built from the address list, since Android already canonicalizes a conversation's membership) — a wordless placeholder becomes "Photo"/"Video"/"Attachment" (`Codex.Domain.Timeline.AttachmentSummary`, shared with the download-completion notification) via `SmsLogReader.ReadMmsAttachments` reading the message's non-text parts (image/video, `application/smil` excluded — that part is the MMS layout description, not content), and a message with one is offered through the Mailbox's existing long-press action card (mirroring how `MailReaderActivity` already offers email attachments) via a new `MmsAttachments.Fetch`, a local `content://mms/part/<id>` read rather than a network fetch since the bytes are already on the device. **Known, accepted gap:** participants can end up including the device's own number — an incoming group MMS's address list often lists every recipient, yourself included, and nothing in the provider says which one that is, so a group header can show one extra name rather than risk dropping a real one.
  - **Group replies: Post now sends one MMS to everyone instead of having nowhere to reply at all.** Reading group MMS into one thread surfaced that the reverse direction had never been built — `MailboxArea`'s reply bar and long-press "Text back" both refused a group thread outright, and even where they didn't, the only send path (`SmsSender.Send`) is single-recipient plain SMS with no attachment support. `Codex.Domain.Post.MmsComposer` writes an M-Send.req PDU (multiple `To` fields — one per participant, so every recipient sees the others, not N fragmented 1:1 copies — always `application/vnd.wap.multipart.mixed`, never a SMIL `multipart/related` slideshow, since Post attaches rather than stages a presentation; every content-type is written as literal WSP Extension-Media text rather than the ~130-entry well-known-type table, which is legal everywhere the table's short-integer form is), verified by decoding its own output with an independent reader in `MmsComposerTests` rather than trusting that a length looked right. `MmsSender` writes the PDU to a FileProvider file, grants the platform's MMS transport read access to it (`MmsAccess.GrantToPlatform` — needed for a Uri from Post's own provider the way it is not for `content://mms` itself, which the SMS role already covers; applied retroactively to the download path too, which needed the mirror-image write grant and was missing it), and calls `SmsManager.SendMultimediaMessage`. `MmsSendReceiver` gets the completion callback and writes the local Sent record — thread id resolved via `Telephony.Threads.GetOrCreateThreadId` against the same participant set, so the reply lands in the SAME thread rather than a new one keyed slightly differently — reading recipients/text/attachments back out of the PDU file itself (`Codex.Domain.Post.MmsSendRequestParser`, a companion decoder scoped to exactly what `MmsComposer` writes) rather than an in-memory handoff, since a plain field would be lost if Android reclaimed the process while an MMS send sat on the network for the 10-60+ seconds those can take. A failed send is not caught by anything synchronous (there is nothing to catch — the platform call returns before it knows) so it is recorded (`PendingMmsSendFailureStore`) and surfaced as a dog-ear notice on the Mailbox's next open, the same "wait behind the fold" shape as the SMS role's own notice and the call-note prompt. Text and a photo/video are two separate sends from one compose dialog (`ShowGroupCompose`, reached from both the reply bar and the per-message action card) rather than one captioned attachment — matching the bridge's own existing "Photo" button precedent, and simpler than it needs to be for now. **Not yet verified on-device, and the riskiest unverified piece of the two MMS phases so far:** `com.android.mms.service` (the URI-permission grant target) is the standard AOSP MMS transport package name across mainstream Android but has not been confirmed as this device's actual one; a real carrier's MMSC is also the first real test of a hand-built PDU actually being accepted rather than silently mangled.
  - **A gap review of the group work found one silent no-op and one crash risk, both fixed; a third finding is a known, accepted limitation.** Filing or deleting a whole correspondence from the Mailbox list (`ShowRowActions` → `FileCorrespondence`/`DeleteCorrespondence`) resolved its items with `ItemsFor(row.ContactKey)`, matching against each item's own `ContactKey` — for a group thread that key is `"group:<id>"`, which matches no individual message's `ContactKey` at all (a group item's own key is whichever address stood in for it, never the thread key), so both actions silently did nothing for any group row, with no error. Group threading is what made this reachable for the first time — before it, no row ever carried a group's key. Fixed by giving `ThreadRow` the thread's own already-resolved `Items` list rather than re-deriving membership from a string; `ItemsFor` is gone. Separately, `MmsComposer` read a picked photo/video fully into memory with no size check, so a phone-sized video would build two full in-memory copies (the read, then the wire buffer) before ever reaching the platform, risking an `OutOfMemoryException` instead of a message the owner could act on — now capped at 15 MB (a guess, not a measured carrier limit; most US MMSCs cap well under it) via `MmsAttachmentTooLargeException`, surfaced as a plain-language dog-ear notice. **International recipients: the normalized-address limitation above is now fixed, patched end-to-end rather than at the send path alone.** `MmsSender`'s recipients and `MmsSendReceiver`'s `GetOrCreateThreadId` call had both been reusing `TimelineItem.Participants` — phone numbers already put through `ContactKeyNormalizer.NormalizePhone`, which keeps only the last ten digits for threading/display and was never meant to be a dialable address; a number outside the NANP would go out missing its country code. Fixed by adding a parallel `ParticipantAddresses` list (the original, unnormalized spelling, one entry per distinct `Participants` key) alongside `Participants` on both `TimelineItem` and `ContactThread`. `SmsRecordMapper.MapMms` builds both lists together off one `Dictionary<string,string>` keyed by the normalized value, keeping the first raw spelling seen per key, so the two lists describe the same people in the same order. `TimelineMerger.BuildThread` re-unions `ParticipantAddresses` across a thread's items by normalized key (not a plain `Distinct()`) because two messages in the same group can each have picked a different first-seen raw spelling for the same person — the merge needs exactly one address per participant, not one per spelling. `TimelineCache` persists the new column following the existing `AddedColumns` migration pattern. `MailboxArea` carries an `openParticipantAddresses` field alongside `openParticipants`, and both `ShowGroupCompose` call sites (the action-row "Text" button and the item action card's "Text back") now send to `openParticipantAddresses`, falling back to the normalized `openParticipants` only if the raw list is empty (an older cached thread from before this column existed). `Participants` remains the matching/display list; `ParticipantAddresses` is what anything that has to actually reach a number reads from. Not yet verified against a real international send — the fix is provably correct at the domain-mapping and merge level (unit-tested, including a mixed-spelling merge case) but nothing here has met a live carrier.
  - **Mail is moving to the Gmail API** (`Codex.Infrastructure/Email/GmailApiClient.cs`), which buys a **real trash** (recoverable 30 days, not IMAP's move-to-a-folder) and **server-side search**.   - **Filing, and the tombstone rule** (`Codex.Domain/Post/Tombstones.cs`) — the phase's load-bearing invariant. Filing means *delete at the source, keep a ghost*; reconcile mirrors the source, so the two cannot both be naive or a filed message reappears forever. Filing writes a tombstone and hides the item at once, the source delete is retried on every sync, **reconcile suppresses anything tombstoned**, and a confirmed delete drops the tombstone. A delete that keeps failing earns a fold but the item stays filed — the owner's intent stands whatever the server does. The **ghost archive** (`GhostArchive`, `FilingStore` tables in `timeline.db`) is separate from the live cache because the cache is rebuilt from the source and the ghost is the only copy left; a ghost is stored as the whole serialized item so no schema omission can drop a field from the last copy of a message.
  - **Sorting and ageing:** `MailRules` first (List-Unsubscribe, no-reply, bill language), one `MailReadingClient` call for what the rules cannot place — classification *and* date detection together, because the second question is free once the message is being read. Every failure there is silent and returns "no idea": rules-only is a working Post, no mail is not. Lifetimes are marketing 1 day, newsletters 1 week, transactional 2 days, **bills never**; aged-out trivia is *gone*, not filed. Correcting a sender (`SenderPromotions`) is permanent. The class is COALESCEd on upsert so a re-sync — which re-reads the message from a source that knows nothing about the sorting — cannot undo the judgement.

### Streaming (Score, decided WS2)

### Folio (project folder `Storyboarder/`, namespaces `Folio.*`)

An **Android (MAUI) app** — user-facing name **Folio**, formerly Canonizer, before that Storyboarder — that reads a novel manuscript and hands the author back a **revision report**: the whole book read fifteen times over by fifteen different voices, and the manuscript itself returned with the findings written on it. P10 renamed it and rebuilt the document around one rule — **anything anchored to a place in the text lives on the text; anything about the book as a whole stays a section** — which turned the marked-up manuscript from an addition into the centre of the report. Gate deliverables live in the project folder: `FOLIO-P10-TECHNICAL-FINDING.md` (approved) and `FOLIO-P10-PLAN.md`.

**The mockups are the specification** and every UI or renderer task builds from them 1:1, surfacing anything that cannot be built as drawn rather than substituting: `https://claude.ai/code/artifact/f540076c-08d0-489b-8183-877f828214d2`

Four **load-bearing principles** survive from the pivot: **nudge never write** (diagnose and point, never ghost-write prose) · **both ends of the pendulum** (flag under- *and* over-writing) · **the report is the star** (the image is evidence) · **quiet by default** (silent Drive delivery, one in-app note, no push or toast).

### Vector documents (cross-cutting)

Every document in the suite was a **150-DPI PNG per page** wrapped by PdfSharp — a picture of a page: nothing selectable or searchable, roughly ten times the bytes on a full page, and resampled twice on e-ink, which is what made small type look soft. **`Storyworthtelling.Paper/VectorPdfSink`** sends the same Skia draw calls to `SKDocument.CreatePdf` instead of a bitmap, so text stays text and fonts are embedded. Foreword's `SkiaPageLayout` draws through it; the draw calls were unchanged by the move, since a PDF's user space is already points — the raster path only scaled because a bitmap has pixels.

**The size claim is reproduced in a test rather than cited**, and the first version of that test failed for the right reason: on a nearly blank page the vector PDF is *larger* (75,700 bytes against 17,442), because a PDF embeds its fonts as a fixed ~75 KB cost while an almost-white PNG compresses to nothing. On five realistic pages it measures **162,075 vector against 1,656,186 raster** (~10×), and a second test pins the mechanism — five pages cost less than twice one, because the fonts are embedded once. Tests read the PDF back with **PdfPig** (the reader Folio already uses) and assert the text is extractable, that images survive on a vector page (D5), and that the pages still merge with the NYT crossword PDF through PdfSharp.

**`PaperTypeScale`** is the printed ladder — the screen ladder at a registered `Ratio` of 0.75 (D30, DESIGN.md §19) — replacing eight ad-hoc point sizes across the composers, with a guard that no composer picks a size or names an `SKColors.*` instead of a Paper & Ink role. The ground is the one exempted colour: the sheets stay white for the newspaper look, a standing decision rather than an oversight.

### The MAUI kit (cross-cutting)

A shared **`Storyworthtelling.Maui`** library (repo root, own `.csproj` + `.Tests`) carries the Paper & Ink role table, the component styles and the eight fonts for the MAUI heads — the counterpart of `Codex.Ui.Android`'s `PaperUi`/`PaperTheme`, which had no MAUI equivalent. Pieces: `Resources/Styles/Paper.xaml` (a **registered token file**, DESIGN.md §19, carrying an `x:Class` so a head can merge it — a XAML `Source=` resolves only inside its own assembly, so heads do `Resources.MergedDictionaries.Add(new PaperKit())` in `App.xaml.cs`), and `PaperFonts.Register` (passed straight to `ConfigureFonts`).

**It exists because the design system was written twice and enforced once.** Each MAUI head kept a private copy of the palette and a leak-guard test holding a *second* hand-typed copy to check it against, so both could be wrong together — and were. Four live bugs came out of the first parity run against `PaperColorTokens`: the accent was still the **retired terracotta** (`#C2542F`) rather than the Action role's pine, **Display** drew in Serif Semibold where DESIGN.md §4 gives every screen header Serif **Black**, the **Label** role took the full ink instead of the muted one, and the **owner's voice had no style at all**. The last two share a cause worth remembering: `SourceSerif4-Black.ttf` and `PinyonScript-Regular.ttf` shipped inside every APK with **no alias registered**, and an unregistered family is not an error in MAUI — the platform substitutes the system face and says nothing.

**The pure halves are pulled out and tested for real.** `Layout/BinderTabLayout` and
`DesignTokens` (Space + Shape only — type sizes stay in the registered `Paper.xaml`) are copies of
`Codex.Domain`'s, kept identical by a **source-level** parity guard rather than by a test that
restates a few remembered values. `State/DogEarState` is new: DESIGN.md §13's rule that an undo
**outranks** a waiting notice and hands the corner back when its window closes had only ever existed
inside the native view, tangled with the host layout, a weak table and a `Handler`, so nothing tested
it. It is now a decision with time passed in. The test project compiles those files directly
(`<Compile Include="..\Storyworthtelling.Maui\...">`), so the real types are exercised — the kit's
own TFM makes a project reference impossible.

**The components** are the binder tab strip, the dog-ear, list rows with the §7 checkbox, and the
accordion picker; the status line and card groups are styles in the dictionary. The strip is the *native*
shape by decision — a glyph over a horizontal label filling the 66dp gutter, the same component
Score and Post draw — so all five apps reach for one divider; `BinderArea` carries **two** glyph
sources rather than one tinted at runtime, because MAUI has no equivalent of Android's
`SetColorFilter` and the only ready answer is a toolkit dependency. The dog-ear is Post's `FoldView`
geometry member for member (two triangles: the **hole** showing what the fold carries, and the
**flap**, the corner turned over and lying back across the page), painted through a `GraphicsView`
`IDrawable`; `DogEarState` decides, the view paints and owns the clock — the state takes time as an
argument, which is what makes it testable. Every view reads its tokens through
**`PaperResources.Token`**, one place because the rule is easy to get subtly wrong: a
`ResourceDictionary`'s indexer looks only at its own entries while `TryGetValue` walks what has been
merged in, so the indexer appears to work until the kit is the only source left. The **wash** tier
lives in the dictionary as 8-digit ARGB and the palette guard *composes* it from the role's mark and
`PaperColorTokens.WashAlpha` rather than trusting the digits.

The kit is `net10.0-android`, so `build-shared-libs` can only run its **tests**; its compilation is proven by the heads that reference it, which is why `Storyworthtelling.Maui/**` is in `build-android.yml`'s path filter and why the guards read files rather than load types. ### Self-update (cross-cutting)

A shared **`Storyworthtelling.Updates`** library (repo root, own `.csproj` + `.Tests`, `net10.0`, pure .NET) owns the decisions behind the rolling **`apps-latest`** GitHub release channel, extracted from Flyleaf's `UpdateService` — which had been the only implementation and so the only place the rules existed. Pieces: `InstallCandidate`, `SuiteApps` (the `com.storyworthtelling.` prefix that is the channel's whole trust boundary), `SiblingUpdatePlan`, `UpdateRunResult`/`AppInstallResult`/`InstallOutcome`/`InstallOutcomes`, and **`UpdateScope.Decide(role, selfPackage, …)`**. `Codex.Domain`'s `PolicyContext.OwnerPackagePrefix` keeps its own copy so Domain stays dependency-free, kept identical by a `FrozenInvariantsTests` parity guard.

**`UpdateScope.Decide(role, selfPackage, …)` answers "which of this release's APKs do *I* install?", and the answer depends on the device rather than the app.** `Custodian` installs for the whole suite — newer or not-yet-installed — and is what **Flyleaf** does on the locked phone, because as device owner it is the only thing that can install silently at all (`ApkInstaller` is device-owner-only and `NoInstallUnknownSources` stays on). `SelfOnly` keeps just the running app current, and is for an **unrestricted** phone where each app can run the confirmed installer itself (Ashley's install, B8). **Decided deliberately:** the launcher stays the single point of failure for updates on the locked phone rather than opening an exported install service on it — the lockdown's install restriction is worth more than the redundancy. Both roles gate on the owner namespace first, which is never a device question.

### Secrets vault (cross-cutting)

Every app's keys and durable "magic strings" live in **ONE AES-256-GCM-encrypted file in the owner's Google Drive** (`storyworthtelling-secrets.json`), so the FocusPhone cutover's factory reset — which wipes every on-device store — no longer means re-entering every credential by hand. The vault types live in the shared **`Storyworthtelling.Voice`** library under the `Secrets/` folder (`Storyworthtelling.Voice.Secrets`), reusing its existing `IDriveTextFile`/`DriveTextFile` Drive seam: `SecretsVault` (a record with one section per app), `SecretsCrypto` (PBKDF2-SHA256 → AES-GCM, **BCL only**, no new dependency; a wrong passphrase fails the GCM tag as `WrongPassphraseException`), `SecretsEnvelope` (the on-Drive `{version,kdf,iterations,salt,nonce,ciphertext,tag}` shape), `ISecretsVaultStore`/`DriveSecretsVaultStore` (load returns a `SecretsVaultLoadResult` distinguishing Empty/Loaded/WrongPassphrase/Corrupt), and `SecretsVaultService` (the per-app orchestration: `LoadAsync` for restore, `PublishAsync(merge)` for a per-section save that never overwrites a vault it couldn't read). Fully unit-tested in `Storyworthtelling.Voice.Tests/Secrets/`. **Two-way, encrypted:** each app publishes its section on settings-save (and on connect/pair events — Ledger on a Plaid link, Foreword on a reMarkable register, Post on mail settings save) and restores missing values on startup; the owner enters one **passphrase per app** (the single thing NOT in the vault — wiped by the reset, re-entered once, then unlocks the rest). The vault is the **single source of truth for the shared Claude key**, replacing the old plaintext `storyworthtelling-voice-config.json`: `VaultVoiceConfigStore` adapts the vault to the existing `IVoiceConfigStore` seam, so the voice stack is unchanged — MAUI apps swap the DI registration; the FocusPhone `VoiceGreeting`/`MusicTasteService` build it directly. Per-app wiring: MAUI apps add a `VaultPassphrase` to their settings store + a `VaultSync` helper + a restore hook in `MainActivity`; the FocusPhone native heads share `Codex.Ui.Voice.VaultPassphraseStore` + `SecretsVaultAccess` and restore in each head's launch Activity. **Ledger's per-bank Plaid access tokens** (generated on-device, in SQLite) are backed up via `AccountService.GetInstitutionCredentialsAsync`/`RestoreInstitutionsAsync` (unit-tested), so a reset restores every bank without re-linking. **Scope change:** writing the vault needs full `drive`, so Ledger + Foreword widen their token scope from `drive.readonly` to `drive` and FocusPhone's `VoiceGoogleAccount` does the same (the owner re-registers the scope; until then publish/restore degrade quietly and apps keep working from local settings). **Not yet done:** live-API verification on a real device (same as the Voice rollout).

**Vault passphrase field:** the one secret NOT in the vault, so every settings screen shows it **in the clear** (not a masked password field) — it must be read back and set identically in each app, and Android blocks clipboard copy on password-typed fields. (The Gmail app password and Plaid secret stay masked — those aren't the vault key.)

**Reading a key for tooling/automation (dev procedure, no secret stored here):** every shared credential already lives in the vault, so a build/automation step (e.g. the Gemini cover-paint pass) does not need a pasted key — it reads it from Drive. The vault file is `storyworthtelling-secrets.json` in the owner's Drive; decrypt it with the owner's **vault passphrase** (the only thing not stored, supplied at run time) using `Storyworthtelling.Voice.Secrets.SecretsCrypto` (PBKDF2-SHA256 → AES-256-GCM, envelope = `{Version,Kdf,Iterations,Salt,Nonce,Ciphertext,Tag}`), then read the section you need off the `SecretsVault` record: `Gemini.ApiKey`, `Claude.ApiKey`, `GitHubUpdateToken`, etc. The decrypted key is used in-process only — **never commit it, never put it in an artifact, doc, or log.** This is the streamlined path so future phases skip the "where's the key" runaround.

**Credential health → settings declutter (cross-cutting):** because the vault backs up and restores every key, a working key is a done state, not something to keep on screen. Shared, unit-tested types in **`Storyworthtelling.Voice`** under `Health/` (`Storyworthtelling.Voice.Health`): `CredentialHealth`/`CredentialHealthReport` (+ `CredentialHealthCodec` JSON), `AuthFailure.IsHttpCredentialRejection` (401/403, plus Gemini's HTTP-400 `API_KEY_INVALID`), `ICredentialHealthSink` (write seam), and `CredentialFieldState.Decide(isSet, health)` — the pure rule that a key field is shown **only** when it's missing or a live call with it was just rejected; a working key collapses to a "Working ✓" line with a **Replace** button. Each app's API clients report health at their HTTP choke point through an **optional** `ICredentialHealthSink` ctor param (default null, so existing client unit tests are untouched; DI injects it because `AddHttpClient` uses `ActivatorUtilities`), and a Preferences/SharedPreferences-backed `CredentialHealthStore` per head persists the report and is read by the settings screen. Only auth rejections flag a key — throttling/5xx/network are left alone so a blip never falsely reveals a field. Per-app credential ids + classifiers: Folio (`claude`/`gemini`), Ledger (`plaid`, via `PlaidFailure` over Plaid `error_code` — item/token errors are a per-institution concern, not the shared credentials), Foreword (`nyt-api-key`/`nyt-cookie`/`remarkable`/`anthropic`), Post (`gmail-app-password` on the IMAP path and `gmail-account` on the Gmail API one; ids now live in `Codex.Domain/Credentials/CredentialIds.cs` so a client and a settings screen share them rather than each holding a copy) and Launcher (`github-update-token`, via `GitHubReleaseClient`'s status-carrying exception in `UpdateService`). Ledger/Foreword `Infrastructure` gained a `Storyworthtelling.Voice` reference for the seam (Foreword bumped `Google.Apis.Auth` to 1.75.0 to match). Pure logic is unit-tested; the settings-screen wiring in the Android heads is compile-checked in CI, live-verify pending like the rest of the Voice/vault rollout.

    work is never replaced, so the phone runs two schedules or none.
  - **`MainActivity`'s Java name**, which previously had none (it was generated from the
    namespace, so the rename would have moved it).
  - **The nine `PreferenceKeys`**, which were `nameof(TheProperty)` — tidy-looking and a trap,
    since renaming a property renames its key and the stored value is not migrated or reported,
    just not found. The constants' values are the old property names, so no phone notices.
- **The secrets vault section is `SecretsVault.Foreword` in code and `"DailyLoader"` on the
  wire** (`[JsonPropertyName]`). The vault has no naming policy, so a property name *is* the key
  written to the owner's Drive; renaming it plainly would have made every existing vault
  deserialise the section to its empty default, silently, losing the Anthropic key and the
  calendar mapping JSON. Guarded by `VaultWireNamesTests`, whose load-bearing case is written as
  the file actually on Drive rather than as a round trip — a round trip alone passes happily with
  the section renamed at both ends, which is precisely the bug.
- The launcher icon is **native** adaptive-icon resources under `Foreword.Android/Resources/mipmap-*`,
  generated by `Tools/IconStudio` (spec `Foreword`, glyph `Glyphs.FoldedPaper`, resource name
  `ic_launcher` — frozen, since `[Application(Icon=…)]` names it). Never hand-edit them.
- `.github/workflows/generate-keystore.yml` still says `CN=DailyLoader`, deliberately: it is the
  one keystore every `com.storyworthtelling` app signs with, and the certificate already issued
  carries that name.
- **Prayer is isolated by a type, not by care (D15, Release H).** `Foreword.Domain/Prayer/PrayerText`
  is what the owner writes on the prayer page, and the only way to read it is to declare yourself an
  `IPrayerReader` — of which there are **five**, enumerated by `PrayerIsolationTests`: the vision
  transcriber, the pastoral composer, the archive codec's caller, the pages that print it, and the
  rotations editor on the phone. The reflective half of that guard can only see Domain and
  Infrastructure, so a second, **source-level** half scans the Android head too; a sixth reader is a
  decision, not a diff. `ToString()` returns a redaction because interpolation is the one hole a type
  cannot close — C# calls it for you with no cast and no warning. The three public composers (the
  brief's opening, the calendar's narrator, the checklist's coach) take and return **strings**, which
  is what makes "the journal cannot reach them" structural. What *private* does not mean, stated at
  gate 1 and accepted: the page is transcribed, so a vision model reads it. What it means is that
  nothing from it reaches Google Tasks, the calendar, the voice profile, or any shared file.
- **The prayer archive is the only copy, and it is encrypted.** One Drive file
  (`storyworthtelling-prayer-archive.json`) through the shared `Storyworthtelling.Voice`
  `VaultEnvelope` — now **public** rather than copied, since there are three such files — locked with
  the same passphrase the vault uses. The journal page is trashed off the tablet once transcribed, so
  `DrivePrayerArchive.SaveAsync` **reads the file back first and refuses** (`PrayerArchiveLockedException`)
  rather than writing over something it could not decrypt; `PrayerDeliveryService` orders the morning
  read → fold → compose → upload → save → trash so that every step which can fail does so *before*
  the sheet is thrown away. Encryption over plaintext was the owner's decision, cost accepted: lose
  the passphrase and the archive is gone.
- **How something gets onto the prayer list — both ways, by the owner's decision.** A one-off request
  is **written** on the journal page, under an "Add to the list" strip at its foot; a standing list
  prayed through one a day (a missionary list) is **edited on the phone** (`RotationsPage` /
  `RotationEditPage`, neither in the approved mockup set — the idea arrived with the answer).
  `JournalRegions` is the one place the two writable bands' coordinates live, and both the painter and
  the transcription prompt read them from it: a line under the strip becomes a printed request and the
  same line two inches higher stays private, so a disagreement about that boundary would put a private
  thought on a printed page. `RotationPick` is **arithmetic on the date, never a stored cursor** — a
  cursor advances on a morning that never delivered, so a name is skipped and nobody finds out.
- **Nothing is hardcoded to one person (Release I).** Foreword had only ever run on one phone, so one
  person was the answer to three questions nobody had noticed were questions: what a `CalendarEvent`'s
  columns start as, what `CalendarMappingOptions.DefaultColumn` is, and where a hand-written note with
  nobody named on it goes. `Foreword.Domain/Install/OwnerColumn` replaces all three — **inferred, never
  asked**: an address entered on the calendar screen names the person outright, and otherwise the
  signed-in account is compared with the shared vault's `OwnerAccount` (cached per install as
  `CredentialStore.HouseholdAccount` by `VaultSync` on every vault read) — the same account is the
  account holder (`WithMailboxes[0]`), any other is the partner (`WithMailboxes[1]`), and an unowned
  vault proposes nothing. It falls back to what the app did before the answer existed, so a phone that
  has been delivering for months does not change its mind on a version bump. Settings only *says* whose
  phone it is; the old picker is gone.
  `NobodyIsTheDefaultTests` is the guard; naming a person is *not* the offence, since the household
  roster, the per-column hues and the vision prompt all name all four and all of those are about the
  **columns**, which exist on both installs.
- **The shared vault holds household facts; the personal vault holds per-install ones.** This is the
  distinction Release I turns on, and the obvious place to put "whose phone is this" is wrong:
  `CalendarMappingOptions` rides `ForewordSecrets.CalendarMappingJson` inside the **shared**
  `storyworthtelling-secrets.json`, which both installs read and only one writes (`VaultOwnership`), so
  a per-install field there would be restored from the first phone onto the second and its owner's
  handwriting would start filing under somebody else — silently. So `InstallOptions` is its own bag,
  built fresh by the head and never deserialised from a shared document. Since the owner is inferred
  rather than chosen, Foreword no longer writes the `PersonalVault` at all (its `OwnerColumn`/`OwnerPhoto`
  fields stay on the record so existing files still round-trip); Score remains its consumer.
  `SharedVaultHoldsHouseholdFactsTests` enumerates the shared section's fields so a new one is a
  decision.
- **The maker's mark is the owner's drawn mark — the one Folio prints.** The brief's first page used to
  carry a photo medallion (`OwnerMark`, a photo picked in Settings, else `/Branding/owner.png`); it now
  draws **`Storyworthtelling.Paper/OwnersMark`** — the canted oval pierced by an M, moved out of Folio so
  both documents share one path. Folio gives it the jacket's colourway; the brief has no jacket, so it
  takes the page's ink on its own ground, which is Folio's own no-jacket case. The photo picker,
  `OwnerMark`, `MedallionImage` and `MedallionCrop` are deleted (`EmbeddedBranding` remains, now with no
  printing consumer). `ForewordPageTests.TheMarkIsDrawnNotAPhotograph` asserts the first page holds no
  image.
- **Home is found, not asked.** Settings used to ask for the address *and* a latitude/longitude. Now
  `HomeLocator` fills whatever is missing: the address from the account's own home address via the
  People API (`GooglePeopleClient`, scope `user.addresses.read`, asked for **on its own** through
  `DeviceAccountSignIn.TokenFor` rather than added to the delivery token — widening that would put a
  consent screen in front of the calendar and stop the mornings), and the point by geocoding it
  (`GoogleGeocodingClient`, same Maps key, **Geocoding API must be enabled on the project**). A typed
  address always wins; a set point is never re-geocoded. The fields appear only when a lookup comes back
  empty. Unverified on a device: whether the People API's `home` address is the one Maps labels Home for

- **A `CollectionDefinition` on a test class makes xUnit discover nothing at all**, silently — the
  marker has to be its own class. The only sign was a suite going from 75 tests to 74.
- **Prayer delivers in its own `try` inside `DeliveryWorker`**, with its own outcome preference

## Languages & Frameworks

- **Primary**: C# / .NET
- **Frontend** (when needed): Angular
- **Mobile** (when needed): .NET MAUI
- **IDE**: Visual Studio

## Project Structure

Each project lives in a single `.sln` with multiple `.csproj` files — typically split by concern (e.g. `Domain`, `Infrastructure`, `API`, `Tests`). Keep projects coarse-grained until complexity actually demands splitting.

## Architecture Preferences

- Object-oriented; avoid functional-style abstractions that don't fit naturally in C#.
- Controllers handle HTTP; services handle logic; EF Core `DbContext` is the data access layer. Do not add a repository layer on top of `DbContext`.
- Do not access `DbContext` directly from controllers or above the service layer.
- Prefer fewer layers over more. Avoid redundant typecasts and pass-through classes that add no value.
- Use SignalR for pushing real-time updates to clients.
- Expose APIs via controllers with Swagger documentation.

## Code Style

Follow standard Microsoft C# naming conventions throughout. Do not use underscores in any identifier — this includes private fields (use `camelCase`, not `_camelCase`).

## Async

Use `async`/`await` only where I/O actually warrants it or where it will meaningfully improve expected performance. Do not make everything async by default.

## Error Handling

Handle errors where they occur. Propagate failures with a descriptive, specific message and preserve the stack trace for debugging. Do not swallow exceptions or replace them with vague messages.

## Testing

- Unit tests for all logic; integration tests at the API boundary.
- TDD strictly: tests are written before implementation.
- Do not skip or defer tests — untested code is not considered done.

## Dependencies

Only add a dependency if one of these is true:
1. It is already present in the project.
2. It is from Microsoft or another well-established, trusted publisher.
3. It is required to integrate with the specific tool or service being built.

When in doubt, implement it directly in C#.

## Git Workflow

- **Never push to `main`**. All changes go on a feature branch for review first.
- Open a pull request and wait for approval before merging.

## Graphify

A local code-knowledge-graph CLI (`graphifyy` on PyPI, installed via `uv tool install graphifyy`; binary is `graphify`). Parses the repo with tree-sitter — no code leaves the machine; only doc/PDF/image extraction (unused so far here — see below) optionally calls an LLM. Installed project-scoped (`.claude/skills/graphify/SKILL.md`, `.claude/CLAUDE.md`) **with `--strict` enabled**.

- **Enforcement, not just documentation.** Documenting a tool in CLAUDE.md doesn't make it get used — verified the hard way: after writing the paragraphs below, raw `grep`/`Read` calls kept happening anyway, nudge or no nudge. Three layers exist and only the last one actually gates anything: (1) the `graphify` skill's own trigger description, (2) this prose, (3) the `PreToolUse` hooks in `.claude/settings.json` (`graphify hook-guard search|read --strict`). Bash/Grep and Glob stay **nudge-only forever** (a shell command has no single parseable target to gate on — see graphify's own hook source, `_run_hook_guard`'s docstring). `Read`, in `--strict` mode, actually **denies** — via `permissionDecision: "deny"` in the hook's JSON, not a nonzero exit — the first in-project read of a file the graph indexes and isn't stale for, once per session, with a message pointing at `graphify query`/`path`/`explain`; re-issuing the same Read afterward succeeds. Confirmed live in this session: it denied a real `Read` of this file mid-edit, a `graphify query` unblocked it, and the retry went through with no further block that session. A stale-for-that-file graph, a non-`Read` tool, or a second `Read` in the same session all fall through to the plain nudge — it can't strand an agent, only cost it one query.

- **Best practice, and it's now externally corroborated, not just our own finding.** Ran a real A/B test on this repo (3 real work items — a feature, a bug hunt, a doc rewritten from source — each done twice, once with graphify, once without, in isolated worktrees): graphify-ON used *more* tokens overall than OFF across the three (1,043,602 vs 984,852), though it finished faster wall-clock (44.9 vs 54.2 min). Separately, an independent published benchmark (github.com/Graphify-Labs/graphify's own honest reviewers, not vendor marketing) found the same shape of result and named the cause directly: graphify helps **architectural exploration of unfamiliar code** (god nodes, blast radius, "what connects to what" in a codebase you don't already know) and is **"unhelpful during focused implementation sessions with clear specifications"** — which is most of what a coding agent is actually asked to do here. **Don't trust the marketed multiples** either: the viral "71.5x" figure is from a mixed corpus where PDFs/images inflate the raw-file baseline; the same benchmark's real number on a pure-code repo was **7.3x**, and only for exploratory questions on an unfamiliar codebase, not routine engineering. **Don't trust graphify's own cost tracker either** — it reports 0 tokens for the AST/CPU-only steps (true, verified independently above) but silently omits any subagent token usage spent *around* those steps, which is where the real cost usually is.
- **Query instead of grepping — but seed it with real identifiers, not a question.** `graphify query "<terms>"` does BFS from whichever graph nodes best match each *word* in the string, not semantic understanding of a sentence. `graphify query "How does a bad API key get detected and cause a settings field to reappear?"` matched on "Settings"/"Key"/"ApiKey" and returned 13 nodes of noise (NYT API options, an unrelated test method) — nothing about credential health. `graphify query "CredentialFieldState CredentialHealth AuthFailure ICredentialHealthSink"` (the actual type names) found the real chain in the same second, and surfaced something a manual grep pass missed on the first try: four apps (Foreword, Ledger, Folio, FocusPhone) each have their own `CredentialHealthStore` implementing the same pattern. **So: skim `graphify god-nodes` or a quick grep for the relevant type/method names first, then feed those names to `query`.** `graphify path "<A>" "<B>"` (add `--undirected` if the directed search comes back empty) and `graphify explain "<concept>"` are similarly name-seeded, not question-seeded, and both stay at file/import granularity — they didn't surface the `MarkFailing()`-write → `CredentialFieldState.Decide()`-read data flow (it crosses a Preferences/Drive persistence boundary, not a direct call), only that both sides import the same namespace. `graphify god-nodes` for architectural hubs. All of this reads `graphify-out/graph.json` directly (~1s, no LLM). Fall back to `GRAPH_REPORT.md` or raw grep when even a symbol-seeded query comes back empty, or when tracing a flow that crosses a persistence/IPC boundary the graph doesn't model.
- **Nothing under `graphify-out/` is committed — rebuild it fresh each session.** `graphify update . --no-cluster && graphify cluster-only . --no-label --no-viz` (~25s cold on this repo's 1342 files, ~1-2s incremental within a session via the AST cache). Both steps are local CPU work only — `--code-only` extraction never touches the network and `--no-label` skips the one LLM-calling step that exists — so a rebuild costs wall-clock time, **not tokens or API spend**; there's no reason not to just redo it. `update` alone re-extracts (content-hash-keyed, so it's cheap even after a big pull) but does *not* re-run clustering, so community numbers/`GRAPH_REPORT.md` go stale until `cluster-only` runs too. `--no-label` skips LLM community naming (no backend key configured here — communities are `Community N` placeholders); drop it and set e.g. `GEMINI_API_KEY`/`ANTHROPIC_API_KEY` if named communities are ever wanted (that step *does* call an LLM and cost tokens/API spend, unlike everything else here).
- **Why it's gitignored, not committed:** first tried committing `graph.json`/`GRAPH_REPORT.md`/`manifest.json`/`.graphify_analysis.json` for instant fresh-clone access. Turned out community-ID assignment isn't stable across `cluster-only` runs — a 2-line CLAUDE.md edit produced a 35%-churned, ~30MB diff (298,074 of 846,056 lines) with no real code change behind it. Two commits alone added ~61MB of permanent blob history for a few lines of real change. Since the rebuild is free of token/API cost, that trade isn't worth it — `graphify-out/` (the whole directory: cache, graph.json, GRAPH_REPORT.md, manifest.json, .graphify_analysis.json, cost.json if an LLM-backed step ever runs) is gitignored, and every session just rebuilds on first use.
- **`.claude/hooks/session-start.sh` rebuilds the graph automatically at the start of every remote session** (same `update`/`cluster-only` pair, non-fatal on failure) — a fresh checkout means a fresh clone had no `graphify-out/` to trigger the skill's own "especially when this exists" heuristic *or* to give `--strict` something to enforce against, so this closes that gap without anyone needing to remember to run it. Confirmed on a from-scratch `graphify-out/`: the hook rebuilds in ~13s and the graph is queryable immediately after. **That hook is remote-only** (`if [ "${CLAUDE_CODE_REMOTE:-}" != "true" ]; then exit 0; fi`) — on a local machine, nothing auto-rebuilds after a `git pull`; graphify's own README suggests a pull alias for exactly this (`git config --global alias.gpull '!git pull && graphify update .'`), worth setting up locally since the CLAUDE.md instruction to "rebuild after pulls" otherwise relies on remembering.
- **Repo-specific findings from building it here:** `--code-only` extraction of the full repo (1342 files: 1267 `.cs` + `.csproj`/`.xaml`/`.sln`/shell scripts) via `tree-sitter-c-sharp` took ~12s and produced 16k+ nodes / 40k+ edges with only **one** parse failure — `Storyworthtelling.Maui.Tests/PaperKitTests.cs:157`, an interpolated verbatim string (`$@"...{family}..."` with embedded `""`) the C# grammar partially mis-parses; the file still contributed 26 extracted symbols, so it's a minor gap, not a blocker. `.yml` workflow files and `.xml`/font/image assets aren't extracted (not classified as code or docs); `god-nodes` output lines up with the real hubs this file already documents (`Codex.Domain.Music`, `Track`, `Novel`, `ForewordTask`, `FolioDbContext`, …), which is a decent sanity check that the graph is trustworthy. Doc/PDF/image extraction (the 44 `.md` files, `.png`/`.jpg` assets) was **not** run — that path needs an LLM call per file and no backend key is set up in this environment; run `graphify extract .` (i.e. drop `--code-only`) to add it later if doc-aware queries become worth the API cost.
